# 昇格レジスタをメモリオペランドのベースにする

## 課題

`register-allocation-2` で昇格レジスタを r/m オペランドと結果の宛先に使えるようにしたが、
**メモリオペランドの*ベース*には使えないまま**である。`:load` / `:store` / `:atomic_*` は
アドレスを一度スクラッチへ移してから参照する。

実測(2026-08-14、`register-allocation-2` 適用後の x86-64、saxpy 1 関数):

```
55: lea (%r14,%rax,4),%r12   ; アドレスは昇格レジスタに入っている
59: mov %r12,%rax            ; ← スクラッチへ移し直している
5c: mov (%rax),%r13d
...
6f: mov %rax,%rcx
72: mov %r12,%rax            ; ← 同じアドレスをもう一度
75: mov %ecx,(%rax)
```

内側ループ 20 命令のうち **3 命令**がこの移し替えである。`mov (%r12),%r13d` /
`mov %ecx,(%r12)` と直接書ければ **20 → 16 命令**の見込み(実装者の見積もり)。

## 影響

arrayscan / sieve のような**添字アクセスが律速のカーネル**に効く。DESIGN N2
(gcc -O2 比 2〜5 倍)は `register-allocation-2` の時点で C カーネル 5 件が
1.09〜2.78x と満たしており、**要件の未達を埋める作業ではない**。

**ただし json が残っている**(2026-08-15 実測、`BENCH_ONLY=ruby BENCH_RUNS=7`):

| ワークロード | v1.0 | 割付後 |
|---|---|---|
| json 2.21.1 | 7.65x | **4.98x** |
| msgpack 1.8.3 | 2.60x | 2.26x |

C カーネルが 7.41x → 1.89x と大きく戻ったのに、**json は 4.98x で N2 の上限ぎりぎり**に
留まった。`register-allocation` が自分で引いた内部目標 3.0x にも届いていない
(あちらは DESIGN N2 の達成をもって閉じ、この残差を本 issue へ申し送った)。

json のパーサ/ジェネレータは**バイト単位のポインタ操作とメモリアクセスに密**で、
本 issue が対象とする形がそのまま並ぶ。**ただしこれは見立てであり、切り分けていない** —
着手時にまず json の hot path を逆アセンブルして、移し替えの `mov` が実際に何割を
占めているかを測ること(ROADMAP §8 H5「推測で最適化しない」)。

## 受け入れ条件

- `:load` / `:store` のベースが昇格レジスタのとき、移し替えの `mov` が出ないこと
  (バイト列テストで固定)
- **ModR/M / SIB の特殊符号化を 3 つとも押さえる**こと。ベースが **r13 / rbp** のとき
  `mod=01` + `disp8=0`、ベースが **r12** のとき SIB を伴う形、REX.B の付与
- `benchmark/run.rb` の C カーネル 5 件で、**gcc -O2 比が悪化しない**こと(ペア計測)
- 全スイートが 0 failures。決定的ビルド(N4)を壊さない

## 作業ログ

### 2026-08-14(起票)

`register-allocation-2` の実装中に見つけ、**その場では直さずに切り出した**。
理由は、この変更が ModR/M/SIB の特殊符号化を**第 2 の面**(アドレッシング)へ広げるもので、
受け入れ条件を満たした割付本体と混ぜるとレビュー範囲が広がりすぎるためである。

`#emit_store` が `load_binary_operands` で rax/rcx を前提に組まれているので、
経路の作り直しを伴う点にも注意する。

### 2026-08-19(着手前の計測 — 前提が実測で否定された)

受け入れ条件が求めていた「**着手時にまず hot path を逆アセンブルして、移し替えの
`mov` が実際に何割を占めているかを測る**」を実施した。

数えたのは、**昇格レジスタ(rbx/r12〜r15)をスクラッチへ移し、その次の命令が
そのスクラッチを間接参照する**対である。この対がちょうど本 issue の対象で、
1 対が 1 命令に畳まれる。上限を与える数え方であり、これ以上には減らない。

| 対象 | 全命令数 | 該当する対 | 割合 |
|---|---:|---:|---:|
| json parser.c | 24,460 | **117** | 0.48% |
| json generator.c | 25,319 | **147** | 0.58% |
| arrayscan | 213 | 2 | 0.9% |
| sieve | 167 | 1 | 0.6% |
| treesum | 286 | 3 | 1.0% |
| mandelbrot / strproc | 136 / 306 | **0** | 0% |

**json に対する前提は否定された。** 起票時に「json のパーサ/ジェネレータはバイト単位の
ポインタ操作に密で、本 issue が対象とする形がそのまま並ぶ」と書いたが、**静的には
0.5% しか出てこない**。5 本しかない昇格レジスタが、実際の拡張コードでは
ポインタ以外の値に取られているためと見られる(これも切り分けていない)。

**見積もり「saxpy 20 → 16 命令」も過大だった。** 実際に該当するのは内側ループ
20 命令のうち **2 か所**で、**20 → 18(10%)**である。残る 2 命令は即値比較など
**別の最適化**の分で、本 issue の対象ではなかった。

```
59: mov %r12,%rax      ← mov (%r12),%r13d に畳める
5c: mov (%rax),%r13d
72: mov %r12,%rax      ← mov %ecx,(%r12) に畳める
75: mov %ecx,(%rax)
```

**静的な数は実行回数を反映しない**ので、ループ内の 2 命令は動的にはもっと効く。
だが json については、静的な出現率が 0.5% である以上、**4.98x の残差を説明する
主因ではありえない**。

## 決着

**着手しない(優先度を下げる)。** 実測が 2 つの前提を否定したためである:

1. **json の残差の主因ではない** — 静的出現率 0.5%。この issue を実装しても
   4.98x はほとんど動かない
2. **見積もりが過大だった** — saxpy で 20 → 16 ではなく 20 → 18(10%)

ポインタを辿る内側ループには 10% 級で効くので**価値がゼロではない**が、
ModR/M / SIB の特殊符号化を**第 2 の面(アドレッシング)へ広げる**代償に対して、
今の優先順位では見合わない。

**json の残差は別の原因を探すべきである。** 次に測るなら、生成コードのプロファイル
(どの関数・どのループに時間が集中しているか)を取り、gcc -O1 の同じ関数と
命令列を比べるのが筋である。**推測で次の最適化を選ばないこと。**
