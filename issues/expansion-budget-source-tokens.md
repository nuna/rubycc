# マクロ展開の予算がソースのトークンまで数え、大きな表を「暴走マクロ」として拒否する

## 課題

**マクロを 1 つも使わない大きな表で、rubycc は「マクロ展開が大きすぎる」と止まる。** gcc は通す。
2026-09-13 にこのホスト(WSL2 / gcc 13.3)で測った。入力は次の形の行を並べた生成ファイルである:

```c
struct e { int a, b, c, d, e, f; };
static const struct e tbl[] = {
  { 1, 2, 3, 4, 5, 6 },
  /* ... この行を N 回 ... */
};
int n(void) { return (int)(sizeof tbl / sizeof tbl[0]); }
```

| N(行数) | gcc | rubycc |
|---|---|---|
| 45,000 | ok | ok |
| 80,000 | ok(1 秒未満) | **`big_table.c:66667:20: error: macro expansion is too large (possible runaway or exponentially expanding macro)`**(約 5 秒) |

**原因はコードに書いてある。** `lib/rubycc/preprocess/preprocessor.rb` の `expand_tokens` は、
**調べたトークン 1 つごとに**予算を 1 消費する(1615 行)。予算 `EXPANSION_TOKEN_LIMIT` は
100 万(187 行)で、翻訳単位ごとに 0 に戻る(546 行)。つまりマクロの生成分だけでなく、
**ソースを素通りするトークンも数えている**。

187 行のコメントは、`<ruby.h>` のヘッダ一式が約 13.7 万を消費するので 100 万なら
**実コードでは発火しない**と書いている。**ヘッダは測ったが、大きな表を持つ本体は測っていなかった。**

## 影響

**実在の gem が落ちる。** コーパス候補 `unicode` 0.4.4.5 は、`ext/unicode/unicode.c:21` で
24,555 行の `unidata.map` を `#include` しており、`unidata.map:17236:38` で上のエラーになる。
その行に暴走するマクロは無い(使っているのは `NULL` だけ)。**対照の gcc はビルドとロードに成功する**
(2026-09-13 実測)。

**診断が誤った原因を指す。** 利用者は存在しない暴走マクロを探すことになる。

## 受け入れ条件

- 上の N = 80,000 の入力がコンパイルでき、`n()` が gcc と同じ値を返す
- **暴走マクロの拒否は保たれる** — 既存の倍々に展開するマクロのテストが、引き続き同程度の時間で
  エラーになる
- `unicode` 0.4.4.5 が rubycc でビルドできる
- `rake test` が 0 failures

## 着手前に確かめること

- **何を数えるか**を決めること。置換で**生まれた**トークンだけを数えれば、上限は
  コメントが述べる意味(暴走の検出)になる。ソースを素通りするトークンは入力の大きさに比例するだけで、
  暴走の兆候ではない
- 暴走マクロの拒否を固定しているテストを先に探し、変更後もそれが同じ理由で落ちることを確かめる
