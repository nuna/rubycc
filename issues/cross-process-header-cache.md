# ヘッダのトークンをプロセスを跨いで再利用し、N1 の未達を詰める

## 課題

DESIGN の N1 は「YJIT 有効時 20,000 行/秒」を目安とするが、v1.0 は**未達**である
(`docs/development/THROUGHPUT.md`、Ruby 4.0.6 + YJIT):

| 指標 | 実測 |
|---|---|
| 代表値 | **13,854 行/秒 = 目標の 69.3%** |
| 外部基準(gcc -O0、同一分母) | 34,874 行/秒(rubycc はその 0.39 倍) |
| sqlite3 amalgamation(261,463 行) | 16,001 行/秒 = 目標の 80.0% |

**残ボトルネックは特定済み**で、ユニークヘッダの**初回字句解析**に収斂している。
Step 108 で同一プロセス内のトークン列メモ化、Step 109 で multiple-include optimization、
Step 110/111 で個別の割り当て削減を入れた結果、**TU 内に残るレバーは 2〜4% 級**であり、
+44%(13,854 → 20,000)には届かない。

`THROUGHPUT.md` は構造的レバーとして**プロセス横断のヘッダトークンキャッシュ**を
M6 へ申し送っている。

## 影響

N1 本来の目的「典型的な gem を数十秒以内」は満たしている(msgpack 11 TU のフルビルドが
2.46 秒)。したがって**利用者の体感が壊れているわけではない**。直す理由は、
rubycc 自身が掲げた要件が未達であること、および `gem install` が複数 TU・複数 gem を
連続で回すため、**プロセスを跨いだ再利用の余地が構造的に大きい**ことである。

## 受け入れ条件

- **代表値 20,000 行/秒以上**(`rake bench:throughput` の中央値、Ruby 4.0.6 + YJIT)。
  **または**、目標値そのものを相対指標へ置き換える判断を根拠つきで記録する
  (`THROUGHPUT.md` の申し送り: gcc -O0 比という外部基準が得られたので
  「gcc -O0 の 0.5 倍」等が候補)
- **決定的ビルド(N4)を壊さない**。キャッシュが効いた実行と効かない実行で、
  生成される `.o` が**バイト一致**すること。`test/test_deterministic_build.rb` に
  キャッシュを跨ぐケースを足す
- キャッシュの無効化が正しいこと — ヘッダが変わったら再解析される。
  **マクロ状態に依存しない範囲(phase 2–3 の scan 結果)だけをキャッシュする**という
  Step 108 の前提を、プロセスを跨いでも保つ
- ペア計測(`BENCH_RUNS=7`、同一セッション連続実行)で改善を示す

## 作業ログ

### 2026-08-13

v1.0 直後の M6 候補として起票。**着手前に決めるべきこと**が 3 つある。

1. **キャッシュの置き場と鍵**。ファイルパス + mtime + サイズか、内容ハッシュか。
   決定性(N4)を守るには、**キャッシュの有無が出力を変えない**ことが絶対条件である
2. **ライフサイクル**。`gem install` の 1 回の中だけか、ユーザのホーム配下に永続化するか。
   永続化すると distroless/読み取り専用 FS での挙動を決める必要がある
3. **目標値の妥当性**。20,000 行/秒という数字は外部基準を持たない時期に置いたもので、
   gcc -O0 が 34,874 行/秒と分かった今、相対指標に置き換える方が意味を持つかもしれない。
   **この判断自体を先に済ませる**(達成不能な目標を追って設計を歪めないため)
