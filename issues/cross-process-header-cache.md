# ヘッダのトークンをプロセスを跨いで再利用し、N1 の未達を詰める

## 課題

DESIGN の N1 は「YJIT 有効時 20,000 行/秒」を目安とするが、v1.0 は**未達**である
(`docs/development/THROUGHPUT.md`、Ruby 4.0.6 + YJIT):

| 指標 | 実測 |
|---|---|
| 代表値 | **13,854 行/秒 = 目標の 69.3%** |
| 外部基準(gcc -O0、同一分母) | 34,874 行/秒(rubycc はその 0.39 倍) |
| sqlite3 amalgamation(261,463 行) | 16,001 行/秒 = 目標の 80.0% |

**残ボトルネックは特定済み**で、ユニークヘッダの**初回字句解析**に収斂している。
Step 108 で同一プロセス内のトークン列メモ化、Step 109 で multiple-include optimization、
Step 110/111 で個別の割り当て削減を入れた結果、**TU 内に残るレバーは 2〜4% 級**であり、
+44%(13,854 → 20,000)には届かない。

`THROUGHPUT.md` は構造的レバーとして**プロセス横断のヘッダトークンキャッシュ**を
M6 へ申し送っている。

## 影響

N1 本来の目的「典型的な gem を数十秒以内」は満たしている(msgpack 11 TU のフルビルドが
2.46 秒)。したがって**利用者の体感が壊れているわけではない**。直す理由は、
rubycc 自身が掲げた要件が未達であること、および `gem install` が複数 TU・複数 gem を
連続で回すため、**プロセスを跨いだ再利用の余地が構造的に大きい**ことである。

## 受け入れ条件

- ~~**代表値 20,000 行/秒以上**、または目標値そのものを置き換える判断を記録する~~ —
  **2026-08-27 に決着した。** 行/秒はゲートから外し、受け入れ条件を N1 本来の
  利用者体感へ戻した(`docs/development/THROUGHPUT.md` の
  「N1 の受け入れ条件と、行/秒の位置づけ」、DESIGN の N1)。
  **したがってこの課題は「要件未達の解消」ではなくなった。**
  残る動機は `gem install` が複数 TU・複数 gem を連続で回すときの実時間短縮である
- **決定的ビルド(N4)を壊さない**。キャッシュが効いた実行と効かない実行で、
  生成される `.o` が**バイト一致**すること。`test/test_deterministic_build.rb` に
  キャッシュを跨ぐケースを足す
- キャッシュの無効化が正しいこと — ヘッダが変わったら再解析される。
  **マクロ状態に依存しない範囲(phase 2–3 の scan 結果)だけをキャッシュする**という
  Step 108 の前提を、プロセスを跨いでも保つ
- ペア計測(`BENCH_RUNS=7`、同一セッション連続実行)で改善を示す

## 作業ログ

### 2026-08-13

v1.0 直後の M6 候補として起票。**着手前に決めるべきこと**が 3 つある。

1. **キャッシュの置き場と鍵**。ファイルパス + mtime + サイズか、内容ハッシュか。
   決定性(N4)を守るには、**キャッシュの有無が出力を変えない**ことが絶対条件である
2. **ライフサイクル**。`gem install` の 1 回の中だけか、ユーザのホーム配下に永続化するか。
   永続化すると distroless/読み取り専用 FS での挙動を決める必要がある
3. **目標値の妥当性**。20,000 行/秒という数字は外部基準を持たない時期に置いたもので、
   gcc -O0 が 34,874 行/秒と分かった今、相対指標に置き換える方が意味を持つかもしれない。
   **この判断自体を先に済ませる**(達成不能な目標を追って設計を歪めないため)

### 2026-08-19(着手前の計測 — 方式が成立しないことが分かった)

**着手前に 2 つ測った。どちらも設計に入る前に答えを出す必要があるものだった。**

#### (1) 現状値の再現で、自分が作った回帰を見つけた

記録の 13,854 行/秒に対し **11,063 行/秒**しか出ず、ペア計測で **12.4% の回帰**と確定した。
原因は直前の最適化 2 段(`spill-traffic-cleanup` / `register-allocation`)で、
**生成コードの速度をコンパイルの速度で買っていた**。
[optimization-pass-throughput](optimization-pass-throughput.md) に切り出し、
約 71% を回収した(master 比 +11.1%)。**この課題より先に片付けた** — 自分で広げた穴を、
より複雑な機構で埋めに行くのは順序が逆だからである。

#### (2) 直列化コストが再スキャンを上回るか — **上回らないが、ほとんど変わらない**

`THROUGHPUT.md` が未検証リスクとして挙げていた点である。`#include <ruby.h>` を含む
翻訳単位を 1 回前処理して走査された **184 ヘッダ**を捕まえ、ヘッダごとに
`Scanner#scan` と `Marshal` の往復を比べた(2026-08-19、Ruby 3.4.5):

| | 合計 |
|---|---:|
| `Scanner#scan` | 256.4 ms |
| `Marshal.load` | **223.9 ms(scan の 0.87 倍)** |
| `Marshal.dump` | 211.5 ms(ヘッダごとに 1 回だけ) |
| キャッシュのサイズ | **5.3 MiB**(1 TU・184 ヘッダ・93,735 トークン) |

**読み戻しても字句解析の 13% しか安くならない。** ヘッダの字句解析はコンパイル全体の
24.4% なので、**効果は全体の約 3%** である。目標に必要な +44% には遠く、
ディスク I/O・キャッシュ無効化の正しさ・N4 の検証面積拡大という代償に見合わない。

**理由は、時間を食っているのが走査ではなく約 9.4 万個のトークンオブジェクトの生成
だからである。** `Marshal.load` も同じ数のオブジェクトを作るので同じ代金を払う。
`THROUGHPUT.md` のボトルネック分析(GC 13.1%、1 コンパイルあたり約 115 万オブジェクト)と
整合する。

**したがって、この方式は「トークン表現の軽量化」(`THROUGHPUT.md` の構造的選択肢 3)を
先にやらない限り成立しない。** 同じ物を作り直す限り、どこから作っても代金は同じである。

再現: `tmp/scan_vs_marshal.rb`(未追跡の計測用スクリプト)。

### 2026-08-27(受け入れ条件の第 1 項が決着した)

行/秒をゲートから外す判断(上記)により、**この課題を「要件未達の解消」として
進める理由は無くなった**。残る動機は実時間の短縮だけで、その見込みは実測で
**全体の約 3%** である。

**方式そのものは、トークン表現の軽量化を先にやらない限り成立しない**(08-19 の測定)。
そこで次の一手を[token-representation-measurement](token-representation-measurement.md)
として切り出した。**この課題の扱い(dropped にするか、軽量化の後に再評価するか)は
その測定結果を見てから決める。**
