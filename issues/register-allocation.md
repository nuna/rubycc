# レジスタ割付を入れて、gcc -O2 比の超過を N2 の範囲に戻す

## 課題

DESIGN の N2 は「gcc -O2 比 2〜5 倍遅を許容」と定めているが、v1.0 は**条件付き達成**である。
実測(`docs/development/BENCHMARKS.md`、gcc -O2 比):

| ケース | 倍率 |
|---|---|
| treesum | 1.22x |
| msgpack | 2.60x |
| strproc | 4.84x |
| mandelbrot | 5.02x |
| sieve | 6.52x |
| arrayscan | 7.41x |
| **json** | **7.65x**(最大) |

超過するのは tight loop 系・計算律速で、制御フロー律速と VM 律速は範囲内である。

**原因は特定・定量化済み**: バックエンドが spill-everything で、**全中間値をスタックに
materialize する**ことの構造的帰結である。同じ「最適化なし」同士の比較である
gcc -O0 比では全ケースが 1.1〜2.9x に収まる。

## 影響

C 拡張は「速いから C で書く」ものなので、計算律速の拡張(json のパース・生成が代表)で
7 倍の差は利用者に見える。v1.0 の README は既知の制限として明記しているが、
**N2 は rubycc 自身が掲げた要件**であり、条件付き達成のまま放置する理由は無い。

## 受け入れ条件

- **`benchmark/run.rb` の全ケースで gcc -O2 比が 5.0x 以内**に収まる
  (現在の最大 7.65x → N2 の上限内)
- **コーパスの合格率が下がらない**(31/34 = 91.2% を維持)。
  バージョニング方針が「合格率の回帰は破壊的変更」と定めているので、これは必須
- 全スイートが 0 failures。**x86-64 と aarch64 の両方**で、差分実行テストが gcc と一致する
- 決定的ビルド(N4)を壊さない。`test/test_deterministic_build.rb` が通る
- 変更前後の実測を `BENCHMARKS.md` に追記する(ペア計測: 同一セッションで連続実行)

## 作業ログ

### 2026-08-13

v1.0 直後の M6 候補として起票。**着手前に決めるべきこと**が 2 つある。

1. **割付の範囲**。全域(グラフ彩色・線形走査)か、まず基本ブロック内に閉じるか。
   後者なら値表現規約(スロット 8 バイト・スカラは 32bit 以上へ拡張済み)との整合が
   取りやすく、`docs/internals/IR.md` の契約を変えずに済む可能性が高い
2. **バックエンドとの境界**。現在は IR ジェネレータが配置を決め、バックエンドは従うだけ
   (`:gp` / `:sse4` / `:mem` 等)。割付をどちらに置くかで、aarch64 側の作業量が変わる

**先に測るべきもの**: どのケースのどの部分で時間を使っているか。7.65x という数字は
「全体が 7.65 倍遅い」であって、「レジスタ割付で 7.65 倍取り戻せる」ではない。
推測で着手しない(ROADMAP §8 H5 の「推測で最適化しない — プロファイルが先」)。
