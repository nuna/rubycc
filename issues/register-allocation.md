# レジスタ割付を入れて、gcc -O2 比の超過を N2 の範囲に戻す

## 課題

DESIGN の N2 は「gcc -O2 比 2〜5 倍遅を許容」と定めているが、v1.0 は**条件付き達成**である。
実測(`docs/development/BENCHMARKS.md`、gcc -O2 比):

| ケース | 倍率 |
|---|---|
| treesum | 1.22x |
| msgpack | 2.60x |
| strproc | 4.84x |
| mandelbrot | 5.02x |
| sieve | 6.52x |
| arrayscan | 7.41x |
| **json** | **7.65x**(最大) |

超過するのは tight loop 系・計算律速で、制御フロー律速と VM 律速は範囲内である。

**原因は特定・定量化済み**: バックエンドが spill-everything で、**全中間値をスタックに
materialize する**ことの構造的帰結である。同じ「最適化なし」同士の比較である
gcc -O0 比では全ケースが 1.1〜2.9x に収まる。

## 影響

C 拡張は「速いから C で書く」ものなので、計算律速の拡張(json のパース・生成が代表)で
7 倍の差は利用者に見える。v1.0 の README は既知の制限として明記しているが、
**N2 は rubycc 自身が掲げた要件**であり、条件付き達成のまま放置する理由は無い。

## 受け入れ条件

- **`benchmark/run.rb` の全ケースで gcc -O2 比が 3.0x 以内**。当初は 5.0x と書いていたが、
  実測(2026-08-13)がそれを保守的すぎると示した — gcc の `-O0 → -O1` は 1.08〜4.62x、
  `-O1 → -O2` は 1.01〜1.14x なので、**割付が効けば -O1 相当(= -O2 の 1.14 倍以内)が
  射程**である。第 1 段([spill-traffic-cleanup](spill-traffic-cleanup.md))の効果と
  合わせて判定する
- ~~**最適化オプション `-O0` / `-O1` / `-O2` を受理し、レベルごとに何を有効にするかを
  決める**~~ / ~~既定のレベルを決める~~ — **2026-08-13 に対象から外した**(下の決定 2)。
  レベルはゲートに使わず、割付は常時有効にする。レベル実装は別 issue に切る
- **コーパスの合格率が下がらない**(31/34 = 91.2%)。バージョニング方針が
  「合格率の回帰は破壊的変更」と定めているので、これは必須。
  **第 1 段([spill-traffic-cleanup](spill-traffic-cleanup.md))の分もここでまとめて測る** —
  あちらは C 機能を足さず全スイートと gcc 差分が通ったため再測を省いたので、
  この計測は 2 段分の合算に対する確認になる
- 全スイートが 0 failures。**x86-64 と AArch64 の両方**で、差分実行テストが gcc と一致する
- 決定的ビルド(N4)を壊さない。`test/test_deterministic_build.rb` が通る
- 変更前後の実測を `BENCHMARKS.md` に追記する(ペア計測: 同一セッションで連続実行)

## 作業ログ

### 2026-08-13(第 2 段に位置づけ直した)

着手前の測定で、**割付より先にやるべきことが見つかった** — rubycc は gcc -O0 に対しても
1.07〜1.97 倍遅く、同じ spill-everything 同士なのだから割付では説明できない差である。
局所変換で取れるその分を第 1 段([spill-traffic-cleanup](spill-traffic-cleanup.md))に
切り出し、**この課題は第 2 段**とした。

測定の要点(2026-08-13、単調時計・5 回中央値):

| 比 | 値 | 意味 |
|---|---|---|
| gcc `-O0 → -O1` | 1.08〜**4.62x** | **割付で狙える上限**(sieve と arrayscan で大きい) |
| gcc `-O1 → -O2` | 1.01〜**1.14x** | 割付以外(ベクトル化ほか)。**主因ではなかった** |

v1.0 直後の M6 候補として起票。**着手前に決めるべきこと**が 2 つある。

#### レベル実装の波及(2026-08-13 に追記)

**(i) 第 1 段の変換はレベルで切り替えない。** 「書いた直後に読み戻さない」「定数を即値で
使う」「添字スケールを `lea` に畳む」は **gcc -O0 もやっている**ことで、最適化ではなく
**素の生成品質**である。`-O0` でも常に有効にする。

**(ii) mkmf は `-O3` を渡してくる。** このホストの `RbConfig::CONFIG["optflags"]` は
`-O3 -fno-fast-math` で、mkmf の生成する Makefile がそのまま `CFLAGS` に載せる。
現在ドライバは `-O` 系を**受理して無視**しているので無害だが、**レベルを実装した瞬間に
コーパスの全 gem が最高レベルでビルドされる**。したがって:

- `-O3` を実装しないなら、**`-O2` へ丸めるのか無視するのか**を決めて文書化する
- **コーパス 34 件の再検証が必須**。合格率の回帰は破壊的変更(README のバージョニング
  方針)なので、レベル実装は**コーパスを回してから**入れる
- N1(コンパイル速度)への影響も測る。gem のビルドが目に見えて遅くなるなら、
  **既定のレベルをどうするか**が別の判断として要る

**(iii) レベルの意味論は gcc / clang の公開ドキュメントから決める。** 他実装のソースは
読まない(R11。chibicc を含む)。決めた内容と根拠は `docs/internals/` に置く
(現時点の仕様であり、実装を変えたら直す文書だから)。

1. **割付の範囲**。全域(グラフ彩色・線形走査)か、まず基本ブロック内に閉じるか。
   後者なら値表現規約(スロット 8 バイト・スカラは 32bit 以上へ拡張済み)との整合が
   取りやすく、`docs/internals/IR.md` の契約を変えずに済む可能性が高い
2. **バックエンドとの境界**。現在は IR ジェネレータが配置を決め、バックエンドは従うだけ
   (`:gp` / `:sse4` / `:mem` 等)。割付をどちらに置くかで、aarch64 側の作業量が変わる

**先に測るべきもの**: どのケースのどの部分で時間を使っているか。7.65x という数字は
「全体が 7.65 倍遅い」であって、「レジスタ割付で 7.65 倍取り戻せる」ではない。
推測で着手しない(ROADMAP §8 H5 の「推測で最適化しない — プロファイルが先」)。

### 2026-08-13(着手 — 測ってから方式を決めた)

**まず測った**(ROADMAP §8 H5「推測で最適化しない」)。`saxpy` 1 関数を第 1 段完了後の
rubycc と gcc -O1 で比べると、**内側ループが 22 命令 対 6 命令**。残っているスロット
往復 11 か所は**すべてブロックをまたぐ値**だった:

| 値 | 毎周の往復 |
|---|---|
| 誘導変数 `i` | ロード 3 回 + ストア 1 回 |
| パラメータ `b` / `a` / `scale` / `n` | ループ不変なのに毎周ロード |

**ブロック内で閉じる値は第 1 段(spill-traffic-cleanup)で既にレジスタ常駐している。**
したがって**基本ブロック内に閉じた割付ではほとんど何も取れない** — 着手前の選択肢
「まず基本ブロック内に閉じるか」は、この実測で消えた。

**決定 1: 関数全域の専有割付にする。** 適格な vreg を選び、**関数の全区間**その
callee-saved レジスタに固定する。**1 vreg = 1 レジスタなので干渉が定義上起きず**、
生存区間解析も干渉グラフも spill 挿入も要らない。第 1 段と同じ「粗いが健全な条件で
解析を持たずに済ませる」延長線上にある。レジスタ利用効率は線形走査に劣るが、
**空きは x86-64 で 5 本(rbx / r12〜r15)、AArch64 で 10 本(x19〜x28)**あり、
どちらのバックエンドも現在 1 本も使っていない。

**決定 2: 最適化レベルではゲートしない**(`-O` は受理して無視のまま)。理由は 2 つ。
**挙動が 1 通りなら N4(決定的ビルド)の検証も 1 通り**で済むこと、そして
レベル実装は「`-O3` を渡してくる mkmf の扱い」「既定レベル」「レベルごとの N4 検証」と
**別の判断を 3 つ連れてくる**ためである。gcc は -O0 で割付をしないので**意味論はずれる**が、
その差は文書化して受け入れる。レベル実装が要るとなった時点で別 issue に切る。

**決定 3: 2 ステップに分ける。** `register-allocation-1` が対象選択(ターゲット非依存)と
x86-64、`register-allocation-2` が AArch64。PR を適度な大きさに保つため。

**v1 の適格条件**(いずれも平坦な命令列から決まる):

- `:addr_of` の対象になっていない(アドレスを取られた値はメモリに居なければならない)
- **ベクタレジスタファイルに触れる命令が読み書きしない** — 浮動小数点値もスロット規約に
  従うため、レジスタに載せると xmm ↔ 汎用レジスタの移動が両バックエンドの浮動小数点
  経路すべてに要る。System V には **callee-saved な xmm が 1 本も無い**ことも効くので、
  第 1 版は整数・ポインタに絞る
- 可変長関数(`va_start` がレジスタ退避域を書く)は対象外にする

選択は静的出現回数(後ろ向き分岐で囲まれた区間を重み付け)で、**同点は vreg 番号順**。
選択が命令列だけの関数であることが N4 を守る。

### 2026-08-14(第 1 段・第 2 段 = x86-64 まで実装)

`register-allocation-1`(選択規則 + x86-64 の昇格)と `register-allocation-2`
(昇格レジスタのオペランド直接名指し)を実装した。設計判断の本体は
`docs/development/STEPS.md` の同名 2 節。

**測って分かった重要な事実**: **値をレジスタに置くことと、レジスタを名指すことは
別の作業**だった。第 1 段だけでは saxpy の内側ループが **27 → 32 命令に増え**、
arrayscan が **+6.9% 遅くなった**(メモリ参照は 13 → 2 に落ちているのに)。
`mov` に置き換えただけではメモリ 1 命令がレジスタ 2 命令になり、命令が消えないためである。
第 2 段で **20 命令**まで落ちた(gcc -O1 は 6)。

| カーネル | 昇格前 | 昇格のみ | 第 2 段後 | gcc -O2 比 |
|---|---|---|---|---|
| arrayscan | 1.088 | 1.164 | **0.805** | 1.89x |
| sieve | 1.598 | 1.334 | **1.071** | 2.17x |
| strproc | 3.145 | 3.018 | **2.806** | 2.64x |
| treesum | 1.567 | 1.588 | 1.585 | 1.09x |
| mandelbrot | 1.441 | 1.445 | 1.473 | 2.78x |

**受け入れ条件の「gcc -O2 比 3.0x 以内」は 5 件すべてで満たした。**

**残りは第 3 段(AArch64)とコーパス再測**である。x19〜x28 の 10 本を同じ方式で使う。
選択規則(`IR::Promotion`)はターゲット非依存なので、AArch64 側はレジスタ集合と
符号化だけになる。

**派生した課題**: 昇格レジスタを**メモリオペランドのベース**にする拡張
(`mov (%r12),%r13d`)は本 issue から切り出した
([promoted-register-addressing](promoted-register-addressing.md))。
