# 候補走査の 99% は捨てる gem の全文ダウンロードである

## 課題

`tools/scan_popular_gems.rb` は、ランク窓の gem を**1 件ずつ丸ごとダウンロード**してから
C 拡張の有無を判定する。**ダウンロードしたものの大半は捨てる** — 実測では
ランク 101〜200 で C 拡張を持っていたのは 100 件中 9 件、301〜500 では 200 件中 14 件だった。

**判定に必要な情報は、落とす前に取れる。** `.gem` は tar で、**`metadata.gz` が先頭メンバ**
であり、そこに gemspec の `extensions:` と `files:` が入っている(2026-09-12 実測):

```
nokogiri-1.18.10     4,365,824 bytes | metadata.gz(2120) data.tar.gz(4360167) checksums.yaml.gz(297)
debug_inspector-1.2.0    9,216 bytes | metadata.gz(823)  data.tar.gz(4976)    checksums.yaml.gz(298)
rails-8.1.1              7,168 bytes | metadata.gz(861)  data.tar.gz(2720)    checksums.yaml.gz(296)
```

**rubygems.org は Range 要求に応える**(同日実測)。先頭 16 KB だけ取って
`metadata.gz` を取り出せた:

```
$ curl -r 0-16383 https://rubygems.org/gems/nokogiri-1.18.10.gem   # HTTP 206, 16,384 bytes
$ tar -xOf - metadata.gz | gunzip | grep ^extensions: -A1
extensions:
- ext/nokogiri/extconf.rb
```

**転送量の実測**(人気 gem 10 件の `Content-Length` 合計):

| | バイト数 |
|---|---|
| いまの走査(全文) | **5,818,880** |
| 先頭 8 KB だけ取る場合 | **81,920**(**1.4%**) |

## 影響

**コーパスを 100 件へ広げる指示に対して、これが律速である。** 候補はランク下位にしか
残っていないので、数千ランクを掘る必要がある。いまの速度はランク 100 件あたり
5〜11 分で、そのほとんどが**捨てる gem の転送時間**である。

外部サービスへの負荷という面でもよくない。判定に使わないバイトを 70 倍取っている。

## 受け入れ条件

- 走査が 2 段になっている。**第 1 段は Range 要求で `metadata.gz` だけを取り**、
  `extensions:` と `files:` から「C 拡張を持ちうるか」を判定する。
  **第 2 段(全文取得・SHA-256・深い検査)は第 1 段を通ったものだけ**に走る
- **判定結果が変わらないこと** — 既知の窓(ランク 101〜300)を再走査し、
  `[1]` / `[1b]` / `[2]` / `[3]` の**振り分けが修正前と一致する**ことを実測で示す
- **SHA-256 の provenance は全文から計算する**(第 1 段の断片から作らない)
- `metadata.gz` が取った断片に収まらなかった場合は**全文取得にフォールバック**する。
  黙って候補から落とさない
- artifact に**どの段で落としたか**が残る(「なぜ X は走査されなかったか」に答えられる)
- 転送量と所要時間の削減を実測して記録する

## 着手前に確かめること

- **深い検査は第 2 段に残す。** `bcrypt` の除外根拠は `extconf.rb` の `$objs` に
  `x86.o` が並ぶことで、これは `data.tar.gz` の中にある。**metadata だけでは判定できない**
- `files:` に C++ / `.S` が見えたら第 1 段で落としてよいが、**`files:` は gemspec が
  宣言したものであって、archive の実体とは限らない**。第 1 段は「**落としてよいか**」ではなく
  「**全文を取る価値があるか**」の判定に留めること

## 作業ログ

### 2026-09-12(起票)

コーパスを 100 件へ広げる作業の入口で、走査の遅さが律速だと分かったので測った。
上の数値はすべてこの日の実測である。

**同日、ランク 501〜1500 の走査に 1 時間かかり、`SCAN_WORK` は 1.8 GB になった**
(gem 1,000 件、うち C 拡張は 54 件)。**判定に使うのはそのうち 1.4% である。**
さらにこの走査は 90% 地点で一度落とされ、やり直している — キャッシュが効いたので
2 回目は速かったが、**1 時間の走査を落とせば 1 時間失う**という形は、
前処理を入れれば最初から小さくなる。

## 決着

**解消した**(`scan-metadata-prefilter-1`。設計判断の本文は
[STEPS.md](../docs/development/STEPS.md) の該当節)。

受け入れ条件の照合(2026-09-12、ランク 101〜300、空の `SCAN_WORK` から):

| 条件 | 結果 |
|---|---|
| 走査が 2 段になっている | 第 1 段は `Range: bytes=0-8191`、第 2 段は通ったものだけ |
| **判定結果が変わらない** | ベース `94618c4` の worktree で**修正前のコードを同じ窓で走らせ、出力を diff** した。**追加したサマリ 1 行を除いて完全一致** |
| SHA-256 は全文から | 変更なし。全文を取らなかった gem の `gem_sha256` は `nil` のまま |
| 断片に収まらなければ全文へフォールバック | 206 以外 / メンバ未完結 / ustar 無し / gzip・YAML 失敗 / platform 不一致 / `required_ruby_version` 不一致。**実測で 200 件中 0 件**(4 件はぴったりの長さで再要求して解決) |
| artifact にどの段で落としたかが残る | 各レコードに `decision`(`stage` / `prefilter` / `reason`)、run summary に `prefilter` ブロック |
| 転送量と所要時間の削減を実測 | **10m42s → 2m39s(4.0 倍)**、全文取得 200 → 20 件、**35.8 MB 節約**、work dir 306 MB → 83 MB |

**着手前に確かめることに挙げた 2 点**も守られている — 深い検査は全文側に残し
(`bcrypt` の `$objs` は `data.tar.gz` の中)、第 1 段は「落としてよいか」ではなく
「**全文を取る価値があるか**」の判定に留めた(拡張子の一覧は意図的に上位集合)。
