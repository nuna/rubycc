# `.so` に `.gnu.hash` と RELRO を出す(L5 第三段)

## 課題

ROADMAP §5 の L5 は 3 段構成で計画され、**第三段だけが実装されていない**。
2026-08-27 に master で確認した:

```sh
$ grep -rn "gnu.hash\|gnu_hash" lib/   # → 0 件
$ grep -rni "relro" lib/               # → 0 件
```

`SharedLinker` が出すのは SysV の `.hash` だけである(Step 34。サイズ決定的な
ラダーでバケット数を導出、平均チェイン長 ~1)。**glibc は `.gnu.hash` 不在時に
`.hash` へフォールバックする**ので `dlsym` は動き、Step 34/35 の Fiddle 実走から
現在の 31 件の検証済み gem まで、この構成で通っている。

RELRO(`.got.plt` の読み取り専用化。`PT_GNU_RELRO`)も同じく未実装で、
Step 34 の計画に「ここで検討」とだけ書かれたまま触れられていない。

**第三段が保留された経緯は記録済み**である。Step 54(M2 完了)の残項目にこうある:

> L5 第三段(`.gnu.hash`・RELRO)は適合性の磨き込みとして後続。

その「後続」がどのマイルストーンにも割り当てられないまま M3・M4・M5 が完了した。

## 影響

**動作には影響していない。** `.hash` だけでも dlopen / dlsym は成立し、
コーパス 31/34 = 91.2% はこの構成で達成している。

効くのは 2 点である。**(1) 適合性** — 現代の GNU ツールチェーンが出す `.so` は
両方のハッシュ表を持つので、rubycc の出力は「動くが今どきの綴りではない」状態にある。
**(2) 性能** — `.gnu.hash` のブルームフィルタは、シンボルが**その `.so` に無い**ことを
高速に棄却するためのもので、依存 `.so` が多いほど効く。C 拡張 1 枚を dlopen する
用途では差は小さい。

RELRO は動的リンク後に `.got.plt` を読み取り専用にする**緩和策**で、
無いことが直ちに脆弱性になるわけではないが、配布物としては見劣りする。

**着手の判断材料が無いのが現状の問題**である。効果を測っていないので、
「やる価値があるか」を答えられない。

## 受け入れ条件

**測ってから決める。** 実装を先に置かない:

- `.gnu.hash` を出す `.so`(gcc/GNU ld 製)と出さない `.so`(rubycc 製)で、
  **dlopen + 代表的な dlsym の実測差**を取る。差が測定誤差に埋もれるなら、
  この issue は `dropped` にして再検討条件を書く
- 実装する場合:
  - `readelf -d` / `readelf -S` で `.gnu.hash` と `PT_GNU_RELRO` が出る
  - `eu-elflint`(存在時)が新たな指摘を出さない
  - glibc と musl の両方で dlopen → dlsym → 実呼び出しが通る
    (musl は `.gnu.hash` を読まないので、**`.hash` を残すこと**が条件)
  - N4 の決定的ビルド(`test/test_deterministic_build.rb`)が 0 failures のまま
  - **R11**: binutils の実装コードは読まない。`readelf` の出力から外形を合わせる
    (Step 34 で `.hash` に対して採った方法と同じ)
