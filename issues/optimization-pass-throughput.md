# 最適化 2 段でコンパイル速度が 12.4% 落ちた分を取り返す

## 課題

`spill-traffic-cleanup` と `register-allocation` で生成コードは速くなった(gcc -O2 比
4.84〜7.65x → 1.09〜4.98x)が、**コンパイル速度が落ちた**。

ペア計測(2026-08-15、同一セッションで 3 ラウンド交互、Ruby 4.0.6 + YJIT、
`BENCH_RUNS=5`、`BENCH_GCC=0`):

| ラウンド | 現 master | 最適化前(`94890f2`) | 比 |
|---|---|---|---|
| 1 | 11,632 | 13,354 | 0.871 |
| 2 | 11,831 | 13,502 | 0.876 |
| 3 | 11,820 | 13,486 | 0.876 |

**12.4% の低下**で、3 ラウンドとも同じ向き・同じ幅。旧ツリーが `THROUGHPUT.md` の
記録値 13,854 をほぼ再現しているので、ホストの揺れではない。

内訳(同一ツリーで `IR::Simplify` / `IR::Promotion` を段階的に無効化して交互計測):

| 条件 | 行/秒 | 直前との差 |
|---|---|---|
| 現状(両パス有効) | 11,760 | — |
| `Promotion` 無効 | 12,131 | +3.2% |
| 両パス無効 | 12,517 | +3.2% |
| 最適化前のツリー | 13,4xx | +7.2% |

**IR パスが約 6.4%、バックエンドが約 7.2% でほぼ半々**である。

### 無駄が構造的に見えている箇所

1 関数あたり同じ命令列を **12〜15 回**走査している(必要なのは 3〜4 回):

| 処理 | 回数 | 内訳 |
|---|---|---|
| `known_op?` の全走査 | 4 | `Simplify.run` / `Promotion.candidates` / `transient_vregs` × 2 |
| `read_counts` | 5〜6 | コピー前送り・添字融合・死結果除去(不動点ごと)・`transient_vregs` × 2 |
| `write_counts` | 3 | 同上 |
| `transient_vregs` 自体 | 2 | `Promotion.candidates` と各バックエンドの `compile` が別々に計算 |

`operand_vregs` は**命令ごとに配列を新規生成**するので、走査 1 回につき命令数ぶんの
ゴミが出る。`THROUGHPUT.md` のボトルネック分析では GC が既に 13.1% を占めていた。

バックエンド側は、命令ごとに残余表の更新・昇格/transient の判定・オペランド形の分岐が
増えている。`@transient`(Set)と `@promoted`(Hash)は emit のホットパスで引かれる。

## 影響

N1(YJIT 有効時 20,000 行/秒)は元から未達(69.3%)だったが、**59% まで下がった**。
`cross-process-header-cache` はこの穴を埋める課題であり、**自分で広げた分を、より複雑な
機構(プロセス横断キャッシュ、N4 の検証面積が広がる)で埋めに行くのは順序が逆**である。
先にこちらを取り返す。

## 受け入れ条件

- **生成物がバイト単位で一致すること**。これは純粋な内部リファクタであり、
  `.o` が 1 バイトでも変われば失敗と判定する(ベンチ 5 本 + `examples/m6` を
  sha256 比較。`test_deterministic_build.rb` も通ること)
- 全スイートが 0 failures
- **ペア計測で改善を示す**(同一セッション交互、3 ラウンド以上)。
  IR パス側の 6.4% は**大半が回収できる**見込み。バックエンド側の 7.2% は
  命令ごとに実際に仕事が増えているため**全部は戻らない** — 回収できた分と
  できなかった分を、理由とともに記録する
- 到達値を `THROUGHPUT.md` に追記する

## 作業ログ

### 2026-08-15(起票)

`cross-process-header-cache` の着手前計測(現状値の再現)で判明した。
現状値が記録より 20% 低かったので、ホストの揺れか回帰かをペア計測で切り分けた。

**空のログを結果として受け取りかけた**のも記録しておく。切り分け用ハーネスが
`main if __FILE__ == $PROGRAM_NAME` で守られており、`load` では main が走らない。
最初の実行は 6 条件すべてが 0 バイトのログを残して「完了」し、マーカーだけが
作られていた。**出力の中身を見ずに次へ進んでいたら、誤った内訳で設計判断していた。**

### 2026-08-19(実装 — `optimization-pass-throughput-1`)

`IR::Analysis` を新設し、未知 op の有無・読み/書き回数・transient 集合を**関数 1 本に
つき 1 回**計算して `Simplify` → `Promotion` → バックエンドへ配る形にした。3 つの
書き換えは数え直す代わりに差分更新する。`operand_vregs` の配列生成は yield 形に、
バックエンドの `@transient` / `@promoted` は vreg 添字の配列にした。

外部レビュー(別系統のモデル)の指摘を 1 件反映した — **差分更新の結果が、書き換え後の
命令列を数え直したものと一致することを確かめるテストが無い**。`test/test_ir_analysis.rb`
を新設し、5 つの形(前送り・後方定義ループでの融合・多周回の死結果連鎖・3 つの同居・
書き換え無し)で確かめている。**検算はテスト側の素朴な実装で行い、`lib/` の数え上げ
関数は呼ばない**(同じコードで検算しても意味がないため)。

## 決着

**回帰の約 71% を回収した**(2026-08-19)。

| 条件 | 結果 |
|---|---|
| 生成物がバイト単位で一致 | **532 / 532 一致**(x86-64 / AArch64 × benchmark・examples・c-testsuite 210 本)。`test_deterministic_build.rb` も 0 failures |
| 全スイート 0 failures | **3219 runs / 11427 assertions / 0 failures / 0 errors / 41 skips** |
| ペア計測で改善 | **master 比 +11.1%**(3 ラウンドとも 1.103〜1.120)。最適化前比 0.864 → **0.960** |
| 到達値を THROUGHPUT.md に追記 | 追記済み(推移表 + 経緯の節) |

**残る約 4% は回収しない。** stackprof で後半処理 41.7ms の内訳を見ると
バックエンドの emit が 59% で、最適化前ツリーは同じ部分が 16ms、しかも**より長い
命令列**を吐いていた。差は命令ごとに実際に増えた仕事(残余表の更新・昇格 / transient の
参照・オペランド形の 3 分岐)であり、**最適化の本体そのもの**である。ブランチ上で
両パスを無効化しても全体時間がほぼ変わらない(0.491s → 0.499s)ところまで来ており、
パスの費用がパスの減らした emit 量と相殺している。

設計判断の本体は `docs/development/STEPS.md` の `optimization-pass-throughput-1`。

**N1 は依然として未達**である(目標の 59% → 約 64%)。穴を埋める課題は
