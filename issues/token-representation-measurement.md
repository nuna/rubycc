# トークン表現の重さを測り、軽量化の上限を出す

## 課題

コンパイル時間を食っているのは**走査ではなくトークンオブジェクトの生成**である。
実測(2026-08-19、Ruby 3.4.5、`#include <ruby.h>` を含む 1 TU・184 ヘッダ):

| | 合計 |
|---|---:|
| `Scanner#scan` | 256.4 ms |
| `Marshal.load`(同じトークンを読み戻す) | **223.9 ms(scan の 0.87 倍)** |

**走査を丸ごと省いても 13% しか浮かない。**読み戻しも同じ数のオブジェクトを作るからである。
`THROUGHPUT.md` のボトルネック分析(GC 13.1%、1 コンパイルあたり約 115 万オブジェクト)とも整合する。

`THROUGHPUT.md` は構造的選択肢 3 として「トークン表現の軽量化(`PPToken` → `Front::Token` の
変換をなくす等)」を挙げ、**1 コンパイルあたり約 20 万個の Data 生成を削れる**と見積もっている。
ただし**この見積りは実測されていない**。

## 影響

[cross-process-header-cache](cross-process-header-cache.md) は、この軽量化を先にやらない限り
成立しない(同じ物を作り直す限り、どこから作っても代金は同じ)。あちらの扱いを決めるにも、
まずこちらの上限を知る必要がある。

**軽量化には代償がある。** `PPToken` と `Front::Token` を分けているのは層の分離という
設計上の利点であり、潰せば前処理と字句解析の境界が曖昧になる。
**得られる速度が測れていない段階で、その利点を手放す判断はできない。**

## 受け入れ条件

- 代表 TU(json `parser.c` と `#include <ruby.h>` の 2 本以上)について、次を**実測値**で示す
  - `PPToken` → `Front::Token` の変換が占める時間の割合
  - 各表現の生成個数(`ObjectSpace` 由来の実測。約 20 万個という見積りの検算)
  - トークンごとに持つ必要のないフィールド(`filename` / `source_line` 等)の洗い出し
- **上限の見積り**を出す。「変換を完全になくせたら何%速くなるか」を、
  スライス試作か計測からの外挿で示す(試作は捨ててよい)
- 結果を `docs/development/THROUGHPUT.md` に記録し、
  [cross-process-header-cache](cross-process-header-cache.md) の扱い
  (dropped か、軽量化後に再評価か)を判断できる材料にする
- **この課題では実装しない。** 測って、上限を出して、判断材料にするまで
