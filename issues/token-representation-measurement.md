# トークン表現の重さを測り、軽量化の上限を出す

## 課題

コンパイル時間を食っているのは**走査ではなくトークンオブジェクトの生成**である。
実測(2026-08-19、Ruby 3.4.5、`#include <ruby.h>` を含む 1 TU・184 ヘッダ):

| | 合計 |
|---|---:|
| `Scanner#scan` | 256.4 ms |
| `Marshal.load`(同じトークンを読み戻す) | **223.9 ms(scan の 0.87 倍)** |

**走査を丸ごと省いても 13% しか浮かない。**読み戻しも同じ数のオブジェクトを作るからである。
`THROUGHPUT.md` のボトルネック分析(GC 13.1%、1 コンパイルあたり約 115 万オブジェクト)とも整合する。

`THROUGHPUT.md` は構造的選択肢 3 として「トークン表現の軽量化(`PPToken` → `Front::Token` の
変換をなくす等)」を挙げ、**1 コンパイルあたり約 20 万個の Data 生成を削れる**と見積もっている。
ただし**この見積りは実測されていない**。

## 影響

[cross-process-header-cache](cross-process-header-cache.md) は、この軽量化を先にやらない限り
成立しない(同じ物を作り直す限り、どこから作っても代金は同じ)。あちらの扱いを決めるにも、
まずこちらの上限を知る必要がある。

**軽量化には代償がある。** `PPToken` と `Front::Token` を分けているのは層の分離という
設計上の利点であり、潰せば前処理と字句解析の境界が曖昧になる。
**得られる速度が測れていない段階で、その利点を手放す判断はできない。**

## 受け入れ条件

- 代表 TU(json `parser.c` と `#include <ruby.h>` の 2 本以上)について、次を**実測値**で示す
  - `PPToken` → `Front::Token` の変換が占める時間の割合
  - 各表現の生成個数(`ObjectSpace` 由来の実測。約 20 万個という見積りの検算)
  - トークンごとに持つ必要のないフィールド(`filename` / `source_line` 等)の洗い出し
- **上限の見積り**を出す。「変換を完全になくせたら何%速くなるか」を、
  スライス試作か計測からの外挿で示す(試作は捨ててよい)
- 結果を `docs/development/THROUGHPUT.md` に記録し、
  [cross-process-header-cache](cross-process-header-cache.md) の扱い
  (dropped か、軽量化後に再評価か)を判断できる材料にする
- **この課題では実装しない。** 測って、上限を出して、判断材料にするまで

## 作業ログ

### 2026-08-27(起票)

N1 の受け入れ条件を利用者体感へ戻す判断(`THROUGHPUT.md`)に伴い、
[cross-process-header-cache](cross-process-header-cache.md) の次の一手として切り出した。
**測定を先に置くのは、08-19 に同じやり方で「方式が成立しない」と分かった前例があるため**である。

### 2026-08-27(測定と判断)

Ruby 4.0.6 + YJIT、`RUNS=5` の中央値。数値は `docs/development/THROUGHPUT.md` の
「トークン表現の重さ」に記録した。

| | json `parser.c` | `#include <ruby.h>` |
|---|---:|---:|
| convert が full に占める割合 | **6.7%** | **8.9%** |
| `PPToken` / `Front::Token` 生成 | 145,843 / 52,486 | 103,503 / 28,037 |
| 総オブジェクト生成 | 1,206,074 | 1,070,848 |

**個数の見積りは当たっていた**(約 20 万個 → 実測 198,329)。**それでも上限は 6.7〜8.9%** で、
層の分離を手放す代償に見合わない。**軽量化は実装しない。**

副産物として 2 つ分かった。`PPToken` が `Front::Token` の **2.8 倍**あり、重いのは変換ではなく
**`PPToken` を作りすぎていること**の側であること。そして質量は前処理にあり
(json 53.0%、ヘッダのみの TU で **76.0%**)、**走査以外の前処理が 29〜52%** を占めること。

再現は `measure_tokens.rb`(**未追跡**の計測用スクリプト。`tmp/scan_vs_marshal.rb` と同じ扱い)。
PR #113 で誤ってリポジトリ直下へコミットしてしまい、#114 で消した — 計測器を実行するために
作業ツリーへ複製したものが `git add -A` に巻き込まれた。**コミット前に `git status` を見ること。**

測定器の欠陥を 1 つ踏んだので残す。**カウンタを入れたまま総オブジェクト数を測ると、
`*a` / `**kw` の展開で約 60 万個ぶん水増しされる**(1,801,873 → 1,206,074)。
数える対象と数え方が同じパスに同居してはいけない。

## 決着

上限は full の 6.7〜8.9%。**軽量化は実装しない**と決めた。記録は
`docs/development/THROUGHPUT.md` の「トークン表現の重さ(2026-08-27 実測)」。
これを受けて [cross-process-header-cache](cross-process-header-cache.md) を `dropped` にした。
