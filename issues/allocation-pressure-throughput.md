# 割り当て圧を下げてコンパイル速度を稼ぐ — GC 停止と配列の事前確保を測る

## 課題

N1 の残ボトルネックは**トークンオブジェクトの生成**である。プロセス横断ヘッダ
キャッシュを実測で否定した([cross-process-header-cache](cross-process-header-cache.md))
ときの数字がそれを示している — `Marshal.load` は `Scanner#scan` の **0.87 倍**にしかならず、
**どこから作っても同じ数のオブジェクトを作る代金は同じ**だった。

既存の計測(`docs/development/THROUGHPUT.md`):

| 項目 | 値 |
|---|---|
| GC(marking + sweeping)の自己時間 | **13.1%** |
| 1 コンパイルあたりの割り当て | 約 **115 万オブジェクト**(PPToken 144,899 / Front::Token 51,736 を含む) |
| `StringScanner#scan` ほか | 24.4% |

**まだ試していない手が 2 つある。** どちらも「メモリを使って時間を買う」形で、
コンパイラのアルゴリズムを変えない。

1. **GC を止める(あるいは遅らせる)**。1 TU のコンパイルは寿命の短いプロセスなので、
   走り切るまで回収しないという選択がありうる。`GC.disable` のほか、
   ヒープの初期スロット数を増やして**GC の発生回数自体を減らす**形も含む
2. **トークン配列を事前確保する**。`Scanner#scan` は `tokens = []` に順次
   `<<` している(`lib/rubycc/preprocess/scanner.rb`)。9 万トークン級の配列が
   段階的に再確保されるなら、ソース長から見積もった容量を先に確保する意味がある

## 影響

N1 は目標の約 60〜64% で未達のまま。**構造的レバーが 1 つ潰れた**ので、
アルゴリズムを変えずに割り当て圧だけを下げるこの 2 案は、残った数少ない道である。

**トレードオフはメモリ**である。DESIGN **N6(1 TU あたり 1 GB 以内)**が上限で、
sqlite3 amalgamation(25 万行)の実測が最大 RSS 467 MB だったので、**余裕は 2 倍強しかない**。
GC を止めれば最悪ケースがこれを超えうる。

## 受け入れ条件

- **ペア計測**(同一セッション交互、3 ラウンド以上)で、各案の効果を代表値で示す
- **同時に最大 RSS を測る**。`sqlite3 amalgamation` を含め、**N6(1 GB)を超えないこと**。
  超えるなら採らないか、条件付き(TU のサイズで切り替える等)にする
- 生成物が**バイト単位で一致**すること(割り当て戦略の変更が出力を変えてはならない)
- 全スイートが 0 failures
- 採否と根拠を `THROUGHPUT.md` に追記する。**効かなかった案も、効かなかったと記録する**

## 作業ログ

### 2026-08-19(起票)

`cross-process-header-cache` の否定を受けて、利用者から提案された 2 案を課題化した。
どちらも「割り当てが支配項である」という既存の実測に直接効く形である。

### 2026-08-19(測定 — 片方は効き、片方は効かない)

3 条件 × 3 ラウンド交互、`BENCH_RUNS=5`、`BENCH_GCC=0`、Ruby 4.0.6 + YJIT。
**時間と最大 RSS を同時に**測った。

| 条件 | 代表値(中央値) | 最大 RSS |
|---|---|---|
| 現状 | 13,005 行/秒 | 108 MiB |
| **`GC.disable`**(コンパイル単位) | **13,843 行/秒(+6.4%)** | **181 MiB(+68%)** |
| `RUBY_GC_HEAP_INIT_SLOTS=2000000` | 13,036 行/秒(+0.2%) | 110 MiB |

3 ラウンドとも同じ向き・同じ幅である。**ヒープの初期スロットを増やす案は効かない** —
差は計測誤差の範囲で、RSS も動かない。GC の回数ではなく**回収そのもの**が代金だった
ということである。

**配列の事前確保は測っていない。** Ruby の配列は幾何級数的に伸びるので 9 万要素でも
再確保は 20 回程度で、しかも移動するのはポインタである。加えて **Ruby には C の
`reserve` に相当する API が無い** — `Array.new(n)` は n 個の `nil` を実際に作るので、
「先に容量だけ確保する」ことができず、トークン数を先に数える(ソースを 2 回走査する)か
見積もりで作って余りを切るかになり、**どちらも新しいコストを持ち込む**。GC 側が
+6.4% を出した以上、こちらは費用対効果で後回しとした(**これは見積もりであって実測ではない**)。

## 決着

**却下(2026-08-19、利用者判断)。** スループットの向上に対して RSS の増加が大きく、
費用対効果が見合わない。

| 得るもの | 払うもの |
|---|---|
| +6.4%(13,005 → 13,843 行/秒) | **RSS +68%**(108 → 181 MiB) |

N1 の不足は +44% であり、**この案が埋めるのはその 1/7 にすぎない**。一方で払う
メモリは典型的な TU で 1.68 倍、最悪ケース(sqlite3 amalgamation)では N6(1 GB)の
余裕を 2 割まで削る見込みだった。**残り 37% を別の手で埋めなければならない以上、
最初の 6% でメモリ予算の大半を使う形は取れない。**

3 つの案の結末を記録しておく:

| 案 | 結果 |
|---|---|
| `GC.disable` | +6.4% / RSS +68% → **費用対効果で却下** |
| ヒープ初期スロット増 | **効果なし**(+0.2%、RSS も動かず)。GC の回数ではなく回収そのものが代金だった |
| 配列の事前確保 | **測らず**。Ruby に `reserve` 相当の API が無く、`Array.new(n)` は n 個の `nil` を実際に作るため「容量だけ確保」ができない。トークン数を先に数えるか余りを切るかになり、どちらも新しいコストを持ち込む(**見積もりであって実測ではない**) |

最悪ケースの RSS 実測は**行っていない**。却下したため不要になった。

**N1 に残る道**は `THROUGHPUT.md` の構造的選択肢 3(トークン表現の軽量化)である。
割り当てそのものを減らす方向で、本 issue の 3 案(割り当てはそのままで回収や確保の
戦略を変える)とは別の系統になる。
