# CRLF の行末では行連結(`\` + 改行)が働かない

## 課題

**`\` の直後が `\r\n` だと、rubycc は行連結と認めずに字句エラーにする。** gcc は通す。
2026-09-13 にこのホスト(WSL2 / gcc 14.2)で最小再現を測った:

| 入力(すべて CRLF 改行) | gcc | rubycc |
|---|---|---|
| 単純な `int main(void) { return 0; }` | ok | **ok** |
| 文字列リテラルを `\` で継続 | ok | **`error: unexpected character "\"`** |
| `#define` を `\` で継続 | ok | **同じエラー** |

```c
static const char s[] =⏎
    "ab" \⏎
    "cd";⏎
int main(void) { return s[0]; }⏎      /* ⏎ はすべて CRLF */
```

```
crlf-splice.c:2:10: error: unexpected character "\"
    "ab" \
```

**CRLF 自体は通る**(1 行目)。壊れるのは**行連結の判定だけ**で、`\` の次に
`\n` を期待しているところへ `\r` が来るためである。翻訳フェーズ 1(物理ソース文字の
写像)で `\r\n` を改行として正規化していれば起きない。

## 影響

**実在の gem が落ちる。** コーパス候補 `murmurhash3` 0.1.7 は、`ext/murmurhash3/murmur3.c` が
CRLF で、113 行目が

```c
        "000102030405060708090a0b0c0d0e0f" \
```

と継続しているため `build_load` に失敗する(2026-09-13 実測)。**対照(host gcc)は成功する**ので、
これは環境でも gem の性質でもなく rubycc の欠陥である。

CRLF で配られる gem は珍しくない。**1 行でも継続行があれば落ちる**ので、
落ち方は「ソースの見た目には何も問題が無いのに字句エラー」になり、原因に辿り着きにくい。

## 受け入れ条件

- 上の 3 つの最小再現が **gcc と同じ結果**になる(いずれもコンパイルが通る)
- **`\r` 単独(旧 Mac の改行)を改行として扱わない** — C の規格が要求するのは
  実装定義の行末の写像であって、`\r` を無条件に改行にすることではない。
  gcc の挙動を実測して合わせること
- **文字列リテラルの中の `\r` は保たれる**(`"a\r\nb"` と書いたときのバイト列が変わらない)
- `test/` に CRLF のフィクスチャで固定した回帰テストがある
- `murmurhash3` 0.1.7 が `build_load` を通る(`tools/verify_corpus_candidate.rb`)
- `rake test` が 0 failures
