# 役割別モデル選択・移譲基準

タスクの性質に応じて、メインセッション(Fable)で直接対応するか、専用のカスタムエージェントに移譲するかを判断するための基準。

## 出典

本方針は次の記事を下敷きにしている:

> okkun0524(GENDA Inc.)「サブエージェント活用で Claude Fable 5 をコスパよく運用する」
> 2026-06-12 <https://zenn.dev/genda_jp/articles/b6045575e2e13d>

記事の要点は「設計判断とレビューは上位モデル、コード調査は中位、テスト実行は下位」という
タスク種別ごとのモデル振り分けで、モデルの能力とトークン消費コストの釣り合いを取る、というもの。
以下の表と判断基準は、その考え方を本プロジェクト(rubycc)の作業内容に合わせて具体化したものである。

## 一覧

| タスク | モデル | 担当 |
|---|---|---|
| 計画・設計判断 | Fable | メインセッション |
| 広範なコード調査、シンボル・参照の追跡、構造分析 | Sonnet | [code-explore](../.claude/agents/code-explore.md) |
| ファイル・シンボルが特定済みのピンポイント参照 | Fable | メインセッション(Grep/Read を直接実行) |
| 仕様が確定した実装、機械的な編集、テスト追加 | Sonnet | [implementer](../.claude/agents/implementer.md) |
| 複数ファイルにまたがる実装、原因の切り分けから必要なデバッグ | Opus | [heavy-implementer](../.claude/agents/heavy-implementer.md) |
| テストの実行と合否の要約 | Haiku | [test-runner](../.claude/agents/test-runner.md) |
| **1 ファイルに閉じた単純・無依存の実装が複数ある**(まとめて並列で片づける) | **Luna** | [codex:codex-rescue](#codexcodex-rescueluna-に移譲する場合) を**多重起動** |
| **行き詰まったときに別系統の意見を得る**(2 つ目の実装案・診断・根本原因の深掘り) | **Luna** | 同上(1 本) |
| レビュー、統合・最終確認 | Fable | メインセッション |

## 判断基準の詳細

### メインセッション(Fable)で直接対応する場合
- **計画・設計判断**: アーキテクチャ選定、仕様の曖昧さを解消する意思決定、トレードオフの比較検討など、移譲すると文脈の往復コストが判断の速さを上回るタスク。
- **ピンポイント参照**: 対象のファイルパスやシンボル名がすでに分かっており、単発の Grep/Read で完結する確認作業。エージェント起動のオーバーヘッド(コンテキストの再構築)が見合わない。
- **レビュー・統合・最終確認**: 複数の変更やエージェントの出力を横断的に評価し、最終判断を下す工程。会話全体の文脈を保持している主体が行うべき。

### code-explore(Sonnet)に移譲する場合
- 対象のファイル・シンボルが未特定で、広い範囲を探索する必要がある調査。
- 「Xはどこで定義されているか」「Yを参照している箇所はどこか」といった横断検索。
- 複数ファイル・複数命名規則にまたがる構造分析。
- 読み取り専用。コードは変更しない。

### implementer(Sonnet)に移譲する場合
- 仕様・設計判断がすでに確定しており、実装方針に曖昧さがないタスク。
- リネーム・置換・定型コード追加などの機械的な編集。
- 既存パターンに沿ったテストの追加。
- 単一〜少数ファイルに変更が閉じている場合。

### heavy-implementer(Opus)に移譲する場合
- 変更が複数ファイルにまたがり、一貫性の維持に高度な判断が必要な実装。
- 原因が未特定のバグに対し、再現・切り分け・特定・修正のサイクルを要するデバッグ。
- 影響範囲の見極めが難しく、着手前に追加調査が必要なタスク。

### test-runner(Haiku)に移譲する場合
- テストスイート・特定コマンドの実行と、成功/失敗件数・失敗内容の要約報告のみ。
- テストコードの修正や原因調査は含まない(必要な場合は implementer / heavy-implementer に引き継ぐ)。

### codex:codex-rescue(Luna)に移譲する場合

OpenAI の Codex プラグイン(`/plugin install codex@openai-codex`)が提供するエージェント。
**Claude 系とは別系統の実装**が得られる点がこの枠の価値である。用途は 2 つに限る。

**1. 単純・無依存のタスクが複数あるとき、多重に起動して並列で片づける**
- 条件は 3 つとも満たすこと: **1 ファイルに閉じている**・**仕様が確定している**・
  **タスク間に依存が無い**。
- 依存があるものを並列に投げると、互いの前提が崩れて**片方の結果が無駄になる**。
  1 つでも条件を外れるなら implementer / heavy-implementer に 1 本ずつ渡す。

**2. 行き詰まったときに別系統の意見を得る**(プラグイン自身が推奨する用途)
- 2 つ目の実装案、診断、根本原因の深掘り。
- **こちらは 1 本**。同じ問題に複数投げても、別系統である意味が薄れる。

#### モデルと effort — **設定ファイルに任せ、フラグで渡さない**

| | 値 | 出所 |
|---|---|---|
| モデル | `gpt-5.6-luna` | `.codex/config.toml`(**リポジトリ内**) |
| reasoning effort | `max` | 同上 |

**他のモデルは使わない。**

`.codex/config.toml` は `~/.codex/config.toml` の**上に重なり、書いたキーが勝つ**
(実測: プロジェクト側に存在しないモデル名を置くとホスト側の設定を押しのけて 400 になる)。
**ヘルプは `~/.codex/config.toml` しか挙げていないが、プロジェクト配下も読まれる** —
推測ではなく実測で確かめること。

リポジトリ内に置く理由は、**この取り決めが個人設定では他の作業者に伝わらない**からである。

**`--model` も `--effort` もプラグインに渡してはいけない。** プラグインは既定でどちらも
未設定のまま渡すので、放っておけば上表の設定がそのまま効く。渡すと壊れる:

- **プラグインの `--effort` が受け付けるのは `none`〜`xhigh` までで、`max` が無い**(実測)。
  つまり `--effort` を明示した瞬間、**`max` より低い値に落ちる**。
- `--model` を明示すれば当然その値が優先される。

**「揃えるために明示的に指定する」が、ここでは逆に劣化を招く**という形なので注意すること。

## 移譲時の注意
- カスタムエージェントは独立したコンテキストで起動するため、会話履歴は自動的に共有されない。移譲時は対象ファイル・シンボル・期待する成果物を明示すること。
- 迷った場合は、「調査が必要か(code-explore)」「仕様が確定しているか(implementer)」「複雑さ・不確実性が高いか(heavy-implementer)」の順に切り分けて判断する。
