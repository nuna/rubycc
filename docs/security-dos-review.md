# セキュリティレビュー — DoS 耐性(サプライチェーン攻撃対策)

このドキュメントは、rubycc に**悪意ある入力を食わせて計算資源(CPU・メモリ・
スタック)を枯渇させる DoS** を成立させられないかを点検し、フェイルセーフを
入れた記録である。rubycc は gem のビルド時に、攻撃者が細工しうる入力
(C ソース・ヘッダ・ELF/ar・ライブラリ)を処理するため、サプライチェーン
攻撃の一部として DoS を誘発される懸念がある。

- 初回レビュー実施: 2026-07-14 / 対策実装: **Step 32**(コミット 059d59d
  "Add DoS fail-safes against runaway parsing and macro expansion (Step 32)")
- **再監査実施: 2026-07-28(v1.0 リリース前)/ 対策実装: Step 118・120** — §6 参照。
  §2.1 で対策したはずのパーサ再帰に**未ガードの経路が残っていた**ことを含め、
  6 件の脆弱性を発見・修正した。
- 関連: 設計判断の要約は docs/STEPS.md の Step 32・118・120、負債表は docs/ROADMAP.md §3

## 1. 脅威モデル

rubycc が処理する入力のうち、**攻撃者が内容を制御しうる**もの:

| 入力 | 処理経路 | 攻撃者の制御 |
|---|---|---|
| C ソース / ヘッダ | プリプロセッサ → 字句 → 構文 → IR → コード生成 | gem に同梱される `.c` / `.h`、依存ヘッダ |
| ELF オブジェクト(.o) | `ObjFile::ELFReader`、`Link::PartialLinker` | vendored `.o`、他ツール産の `.o` |
| ar アーカイブ(.a) | `ObjFile::ArReader`、リンカの遅延取り込み | vendored 静的ライブラリ |
| 共有ライブラリ(.so) | `ObjFile::ELFReader`(動的シンボル) | リンク対象の `.so` |

想定する被害は**可用性の破壊**(ビルドがハング、あるいは OOM/スタック枯渇で
異常終了)。任意コード実行やメモリ破壊は Almost Pure Ruby 実装の性質上の対象外だが、
生の `SystemStackError` がプロセス外に漏れて異常終了する事象は「明確なエラーで
拒否する」(N3: 未対応は黙って壊さない)方針に反するため、可用性の問題として
扱う。

## 2. 実証した脆弱性(対策前)

メインセッションで PoC 入力を作成し、対策前の HEAD(42abd08)で実際に再現した。

### 2.1 本体パーサの再帰下降 → `SystemStackError`(生の Ruby 例外)

`lib/rubycc/front/parser.rb` の再帰下降は深さ無制限。深くネストした入力で
Ruby のコールスタックを溢れさせ、**`CompileError` ではなく生の
`SystemStackError`** を送出する。組み込み利用(将来の rmake / rubygems_plugin)で
捕捉されなければプロセスが異常終了する。再現した経路:

| PoC 入力(縮約) | 例外発生箇所 |
|---|---|
| `int x = ((((…((1))…));`(括弧式 6 万段) | `parse_cast_expression` |
| `int x = {{{…}}};`(初期化子 4 万段) | `parse_initializer_list` |
| `int x = !!!…1;`(単項連鎖 8 万段) | 深い単項再帰 |
| `int f(){{{…}}return 0;}`(複合文 6 万段) | `parse_compound_statement` |
| `M((((…))))`(マクロ引数の括弧 7 万段) | `parse_cast_expression` |
| `1?1?…:1:1`(三項 4 万段) | 条件式の再帰 |

### 2.2 `#if` 定数式パーサの再帰下降 → `SystemStackError`

`lib/rubycc/preprocess/constant_expression.rb` の `ConstantExpressionParser` も
同じく深さ無制限。`#if ((((…))))` を数万段で `SystemStackError`。

### 2.3 マクロ展開の指数膨張 → CPU/メモリ枯渇

`lib/rubycc/preprocess/preprocessor.rb#expand_tokens`(作業キュー方式)は
処理量に上限が無い。青染め(per-token `suppress` 配列)は自己参照・相互再帰は
止めるが、**正当な指数増殖**を止められない。PoC:

```c
#define B0 1
#define B1 B0 B0
#define B2 B1 B1
/* … */
#define B40 B39 B39
int x = B40;          /* 2^40 = 約 1 兆トークンへ展開 */
```

`B40` の 1 行で 20 秒経過してもコンパイルが終わらずタイムアウト(CPU・メモリ
とも枯渇へ向かう)。これは gcc でも同様に破綻するが、サプライチェーン防御
としては明示的な上限で早期に打ち切るべきと判断した。

### 2.4 正常系(対策後も無傷であるべき挙動)

以下は対策前から正しく**停止**しており、対策で壊してはならない:

- 相互再帰マクロ `#define A B` / `#define B A` → 青染めで停止(正常)
- `#if 1` … `#endif` の 5 万段ネスト、`int ****…p;`(ポインタ宣言子 10 万段)
  → いずれもループ処理でスタックを消費せず正常終了

## 3. 分析 — 線形有界で「無限/指数ではない」箇所

以下は攻撃者制御下でも**入力サイズに対して線形**で、指数爆発も無限ループも
起こさないことを確認した。ただし巨大 `count` による大配列確保などを未然に
防ぐため、防御的な健全性チェックは入れる(§4-D)。

- **`ObjFile::ELFReader`** の各テーブル走査(セクション数・シンボル数・
  再配置数・動的エントリ数): `count` はセクションの `sh_size` から導かれ、
  各エントリ読み取り時の境界検査(`require_range`)がファイルサイズで頭打ちに
  する。`e_shnum == 0` 時に第 0 セクションの 64bit `sh_size` を数に使う経路も、
  範囲外読み取りで早期 `raise`。
- **`ObjFile::ArReader`**: メンバ走査 `pos = parse_member(pos) while …` は
  `size >= 0` により毎回 60 バイト以上前進するので無限ループにならない。
  シンボルインデックスの `count` も `offsets_end > bytesize` 検査で有界。
- **`Link::PartialLinker`** のアーカイブ遅延取り込みの不動点反復: 取り込み済み
  メンバ集合が単調増加なので必ず停止する。

## 4. 対策(フェイルセーフ)

いずれも「一定回数/深さ/総量で打ち切り、明確なエラーで拒否する」方針。
パーサ・プリプロセッサは既存の `CompileError`(file:line:col + caret 付き)、
リーダは `ELFFormatError` / `ArFormatError` を送出する。

### A. パーサの再帰深さガード(`front/parser.rb`)
共有カウンタ 1 本 + `ensure` 減算の `with_nesting_guard` ヘルパを、ネストが
深くなる各経路に配置: 式の右再帰段(cast / unary / conditional / assignment)、
複合文 `parse_compound_statement`、初期化子リスト `parse_initializer_list`、
宣言子 `parse_declarator_builder`、struct/union 本体。カウンタは全経路共有
(式の中に文、文の中に式が混ざるため深さは合算が正しい)。上限超過で
`SystemStackError` の代わりに located `CompileError`(`... nested too deeply`)。

**上限確定値 `MAX_NESTING_DEPTH = 500`**。当初案 2000 は本環境の実測で無効と判明:
- 実測で**フルパイプライン(パーサ + IR 生成 + コード生成が同一 AST を深く再帰)
  は約 330 段の括弧でスタックが溢れ、300 段は通る**。括弧経路は 1 段あたり
  約 40 Ruby フレームを消費し、単純再帰の限界は約 13,000 フレーム。よってパーサ
  単体で測った 2000 は「ガード発火前に SystemStackError」となり無効だった。
- 経路別の深さ乗数(実測): 括弧 = 4.1x/段(最悪)、単項 = 2.1x、三項/代入/
  複合文/sizeof ≈ 1.1x。
- 実コードの最大ネスト深さ(全ガード有効で実測): c-testsuite 41 / ruby.h
  スモーク 32 / examples 22。
- 500 は括弧を約 122 段まで許容 = C11 §5.2.4.1 の実装下限 63 の約 1.9 倍、
  実コード最大 41 の 12 倍。発火時のフレームは約 4,900(オーバーフロー
  約 13,000 の 38%)で、より深いスタックから呼ばれる環境(CI・埋め込みホスト)
  にも余裕。**パーサ単体でなくフルコンパイル(`Compiler#compile`)で発火前後を
  検証**(63・100 段は完走、40,000 段の全攻撃経路は located CompileError で拒否)。

### B. `#if` 式パーサの再帰深さガード(`preprocess/constant_expression.rb`)
`ConstantExpressionParser` の `parse_conditional`(括弧/三項)・`parse_unary`
(`!!!` / `---` 連鎖)に深さガード。**上限 `MAX_NESTING_DEPTH = 500`**。この軽量
文法(単一の優先順位クライミング)は約 2,500 段で溢れるため、500 は約 250 段で
拒否 = 約 10 倍のスタック余裕。実 `#if`(通常 10 段未満)を大きく上回る。

### C. マクロ展開の総量上限(`preprocess/preprocessor.rb`)
`expand_tokens` の作業キュー処理に、run 全体で消費する累積トークン予算を設け、
超過で `CompileError`(暴走マクロ・指数膨張マクロを早期打ち切り)。併せて
`#if` 条件スタック深さ、マクロ引数のネスト括弧深さにも上限。
- マクロ展開予算 **`EXPANSION_TOKEN_LIMIT = 1_000_000`**(queue.shift ごとに 1
  消費)。実測: `#include <ruby.h>` の前処理は **136,916 トークン**消費 =
  約 7.3 倍の余裕。指数膨張マクロは予算到達までフル処理してから拒否するため
  所要時間 ≈ 予算に比例(実測 500k→1.65s / 1M→3.2s / 2M→6.9s / 8M→27s)。
  7 倍の安全余裕を保ちつつ約 3.2s で打ち切る 1M を採用(当初案 8M は 27s と
  遅すぎるため不採用)。
- `#if` ネスト深さ **`CONDITIONAL_NESTING_LIMIT = 256`**(ヒープ配列でスタック
  非依存だが敵対的入力を上限化)。
- マクロ引数ネスト **`MACRO_ARGUMENT_NESTING_LIMIT = 2000`**(整数カウンタで
  再帰でないためスタック非依存の防御的上限)。

### D. リーダの `count` 健全性チェック(`objfile/elf_reader.rb`, `ar_archive.rb`)
巨大 `count` で大配列を確保・長時間ループする前に、`count` がそのテーブルの
ファイル内バイト範囲 / 最小エントリサイズから導ける最大数を超えていれば即
`ELFFormatError`。リンカの不動点反復の停止性も明示的に確認。

### E. 回帰テスト(`test/test_dos_resilience.rb`)
§2 の PoC を縮約した入力が、**`SystemStackError` やタイムアウトではなく明確な
`CompileError` / `ELFFormatError` で拒否される**こと、および「上限内の
そこそこ深い正当な入力」が従来どおりコンパイルできること(誤検知しないこと)を
検証する。

## 6. v1.0 リリース前の再監査(2026-07-28、Step 118・120)

v1.0 リリース準備の一環として、§1〜§5 の対策が**その後の変更で無効化されていないか**を
点検した。特に M5 H5 の性能最適化(Step 106〜116。スキャナの StringScanner 化、
ヘッダのスキャンキャッシュ、multiple-include optimization、emit 経路の割り当て排除など)
で防御が抜けていないかが主目的である。

体制は、サブエージェント 2 体による独立調査(観点 a: 環境変数など外部入力からの攻撃、
観点 b: 計算量爆発の再精査)と、その報告に対するメインセッションでのコード裏取り。
報告された指摘は**すべて file:line を当たって成立を確認**してから修正に着手した。

### 6.1 §2.1 の再発 — 未ガードの再帰経路が残っていた(最重要の教訓)

**Step 32 の対策(§4-A)は、それが覆った経路については正しかったが、覆っていない
経路があった。** §4-A が列挙するガード配置先は「式の右再帰段・複合文・初期化子リスト・
宣言子・struct/union 本体」であり、**波括弧を伴わない制御構造の本体**
(`if`/`while`/`do`/`for`/`switch`/`case`/`default`/ラベル)が `parse_statement` を
再帰する経路が入っていなかった。

§2.1 の PoC 表を見ると、文のネストは `int f(){{{…}}return 0;}` という**波括弧ありの
複合文**でしか試していない。複合文は `parse_compound_statement` でガードされるため
PoC は正しく拒否され、**波括弧なしの経路は最後まで試されなかった**。

結果として、約 100KB の `void f(void){ if(1)if(1)…; }` が深さカウンタを一切増やさずに
再帰し、§2.1 とまったく同じ症状 — **`CompileError` ではなく生の `SystemStackError`** —
を再現した。`SystemStackError` は `StandardError` ではないため、`lib/rubycc/driver.rb` の
rescue 群(`UsageError` / `CompileError` / `Backend::UnsupportedError` /
`Link::LinkError` / `Errno::ENOENT`)のいずれにも捕まらず未処理例外で終了する。

- **修正(Step 118)**: `parse_nested_statement(token)` ヘルパーを追加し、制御構造が
  本体へ再帰する **9 箇所すべて**(8 メソッド。`if` は then 側と else 側の 2 箇所)を経由させた(複合文内の文の並びは既存のブロック
  ガード配下なので対象外)。`parse_statement` 自体にガードを掛けなかったのは、
  複合文で二重計上になり §4-A で確定した深さ 500 の意味が変わってしまうため。
- **教訓**: 「深さガードを入れた」ことと「**全再帰入口を網羅した**」ことは別である。
  PoC が通る形だけで検証すると、同じクラスの穴が別の入口に残る。今後この種のガードを
  追加・変更するときは、**再帰呼び出し箇所を機械的に列挙して照合する**こと。

### 6.2 新たに発見した計算量爆発(Step 120)

| # | 箇所 | 内容 | 実測 |
|---|---|---|---|
| 1 | `rmake/expander.rb` | `MAX_EXPANSION_DEPTH` は**呼び出しの深さしか数えず**、1 回の展開が同じ変数を複数回参照する**ファンアウト**が無防備。`A_i = $(A_{i-1})$(A_{i-1})` の連鎖は深さ 200 未満のまま 2^n 回展開される。`:=` 代入は**パース時点**で展開されるため、ターゲットを 1 つもビルドせず Makefile の解析だけでハングする | n=20 で 7.3 秒 / 1MB、n≈30 で 1GB 規模 |
| 2 | `preprocess/scanner.rb` | `@ascii_only` をファイル全体で 1 回判定していたため、非 ASCII が **1 バイトでも**あると同一行の全トークンで行頭からの `byteslice` が走る。**UTF-8 BOM やコメント中の日本語だけで発火**し、問題の行と同じ行にある必要すらない | 1.29MB の 1 行で 11.18 秒 |
| 3 | `link/partial_linker.rb` | 未定義シンボルが 1 個解決されるたびに全メンバを再走査。逆順依存のアーカイブで二次。**メンバ順は攻撃者が制御可能** | 3,000 メンバ 10.31 秒 |

**対策**:

1. **総作業量の予算を 2 本立てで導入** — `MAX_EXPANSION_REFERENCES = 100_000` と
   `MAX_EXPANSION_OUTPUT = 4MiB`。空文字列に展開されるファンアウトは**参照数でしか**、
   テキスト量の爆発は**文字数でしか**見えないため両方必要である(§4-C の
   `EXPANSION_TOKEN_LIMIT` が単一予算で足りたのは、プリプロセッサの展開が必ず
   トークンを産むためで、Makefile の変数展開とは性質が違う)。参照上限を実測最大
   (32 参照)の約 3000 倍という小さめの値にしたのは、**上限到達までの時間そのものが
   攻撃者の使える資源**だからである。予算はトップレベル呼び出しごとなので、`:=` を
   多数並べられれば総時間はその本数倍になる。トリップは 0.36 秒。
2. **増分カウント方式**に変更(11.18 → 0.24 秒)。桁の値が変わると診断品質(N3)に
   直結するため、旧実装との突き合わせで実ソース 76 本(BOM・行継続・ブロック
   コメント混在を含む)の全呼び出しが一致することを確認した。
3. **逆引きインデックス + 昇順キュー**(10.31 → 0.64 秒)。取り込み順は決定的ビルド
   (N4)に直結するため厳密に保存し、**旧実装とのランダム 320 ケースの出力 SHA256
   全件一致**で裏取りした。

### 6.3 悪意ある入力を要さない二次時間(Step 118)

`compiler.rb` の `defined_names` / `known_names` が Array のまま `include?` され、
`objfile/elf_writer.rb` の `@undefined_symbols` も同様だった。相互に呼び合うだけの
**普通の** C で関数 8,000 個 1.51 秒 / 16,000 個 3.48 秒 / **32,000 個 16.95 秒**と
明確な二次成長を示した。攻撃入力ではなく、H5 が目標に掲げた「巨大な単一 TU」という
ユースケースそのものを直撃する設計上の見落としである。

修正は membership 専用であることを全使用箇所で確認した上での Set 化。ただし
`@undefined_symbols` は**出力順が決定的ビルド(N4)を決める**ため Array を残し、
判定用の Set を並走させた。

### 6.4 パストラバーサル(Step 118)

`exe/rubycc-ar` の `x`(展開)がメンバ名を無検証で `File.binwrite` のパスに使っていた。
`../../../tmp/evil` というメンバ名を持つ手作りアーカイブで、カレントディレクトリ外へ
任意ファイル書き込みができた(zip-slip 相当)。`ar_archive.rb` の名前解決は短い名前でも
`//` 拡張ネームテーブル経由の長い名前でも `/` や `..` を拒否しない。

修正は、絶対パス / `/` を含む / `.` / `..` / 空 の拒否。**黙って `basename` に書き換えず
明示的にエラーにする** — サイレントに別名で書くと攻撃の痕跡が消えるためである。

なお `$(AR)` への自動差し替えは行われていないため、通常の `gem install` 経路単体では
踏まれない。踏まれるのは、ユーザや Makefile が未検証のアーカイブに対して明示的に
`rubycc-ar x` を実行した場合である。

### 6.5 監査で「問題なし」と判定した領域

対策を要さないと判断した箇所も、**次回の監査で再確認の手間を省くため**記録する。

- **環境変数**: `RUBYCC` / `RUBYCC_HERMETIC_HEADERS` / `PKG_CONFIG_PATH` / `RUBYLIB` /
  `RUBYOPT` / `MAKE` / `PKG_CONFIG` を全参照箇所で確認。いずれも安全性境界を緩めない
  (`RUBYCC_HERMETIC_HEADERS` はヘッダ検索範囲を**狭める**方向にしか動かない)。
  `TMPDIR` / `HOME` / `CC` / `LDSHARED` / `CPP` は**参照箇所自体が存在しない**。
- **プロセス起動**: `Process.spawn`(rmake)と `Open3.capture2e`(doctor)の 2 箇所のみで、
  **いずれも argv 配列渡し**。バッククォート・`%x`・`IO.popen`・`Kernel#open`・裸の `exec` は
  `lib/` `exe/` に皆無。「rmake はシェルを経由しない」という設計文書の主張が
  コードで裏付けられた。
- **一時ファイル**: `Dir.mktmpdir` / `Tempfile` / `/tmp` へのハードコードが `lib/` `exe/` に
  **ゼロ**。予測可能な一時ファイル名やシンボリックリンク競合の攻撃面が存在しない。
- **`#include` の解決**: `../` や絶対パスで検索パス外を読めるが、これは gcc と同じ
  正常な C プリプロセッサ挙動であり、ソース自体が既に信頼境界の内側(extconf.rb と同格)。
- **入力パーサの堅牢性**: §4-D の対策(ELF リーダの `count` 健全性チェック)は健在。
  ar リーダのメンバ走査は `pos` が単調増加するため必ず停止。pkgconf の `Requires` 再帰は
  `visited` で循環ガード済み。
- **プリプロセッサの `EXPANSION_TOKEN_LIMIT`(§4-C)**: 全 3 経路(行走査・`#if` 評価・
  関数マクロの引数事前展開)が同じ `expand_tokens` を通り予算を共有している。
  `#` / `##` は独自ループを持たず、同一引数の多重展開は `invocation.expanded[index] ||=`
  でメモ化済み。**加算漏れなし**。
- **性能最適化で入った新規正規表現**(Step 106 の StringScanner 化): `PP_NUMBER_RE` /
  `STRING_RE` / `CHAR_RE` / `WIDE_*` / `PUNCTUATOR_RE` などを 1 本ずつ、
  「両分岐が競合し最後に失敗する」敵対的入力で n=1,000〜160,000 まで実測し、
  **破滅的バックトラックが無い**ことを確認(各交替の分岐が互いに素な文字クラスで、
  再バックトラックが発生しない)。`splice` / `sync` / `skip_block_comment` も線形。
- **キャッシュ群**(Step 108/110 の `@scan_cache` / `@guard_cache` / `@resolve_cache`):
  いずれも 1 TU ごとに新しい `Preprocessor` インスタンスに閉じており、コストとメモリは
  読んだバイト数に対して線形。増幅経路は見つからなかった。

### 6.6 脅威モデルの精緻化

再監査にあたり、重大度の判断基準を明確にした。**悪意ある gem は extconf.rb で
すでに任意 Ruby コードを実行できる**ので、「悪意ある gem がコード実行できる」こと自体は
新規の脆弱性ではない。現実的に意味があるのは次の 4 点であり、この観点で重大度を判定した:

1. 意図した出力先の外へのファイル読み書き(パストラバーサル、シンボリックリンク追従)
2. シェル注入・意図しないプロセス起動
3. 環境変数による安全性挙動の変化
4. 小さな入力でのハング・メモリ枯渇

この整理により、たとえば「`#include "../../../etc/passwd"` で検索パス外を読める」ことは
**gcc と同じ正常な挙動**として過大評価を避けられた一方、「ar のメンバ名で任意パスに
書ける」ことは 1 に該当する実害として修正対象になった。
