# rubycc コンパイルスループット(N1)の実測と v1.0 判断(M5 H5)

DESIGN 要件 **N1** に対する、M5 H5 の最適化とその結果の記録。

**N1 の文言は 2026-08-27 に改めた**(次節)。以下の「未達」「目標の 69.3%」といった
記述は、**当時の受け入れ条件(20,000 行/秒)に照らした当時の判断**であり、
記録としてそのまま残してある。現在の受け入れ条件は次節を見ること。

ハーネスは [`../benchmark/throughput.rb`](../../benchmark/throughput.rb)
(`rake bench:throughput`)。各実行は `benchmark/results/throughput-<stamp>.{md,json}`
を残す。個々の最適化の設計判断は [`STEPS.md`](STEPS.md) の Step 105〜116 にある。

## N1 の受け入れ条件と、行/秒の位置づけ(2026-08-27 に改めた)

**受け入れ条件は利用者の体感に置く。行/秒はゲートではなく、回帰を検知するための計測値である。**

| | 位置づけ | 現状 |
|---|---|---|
| 典型的な gem のフルビルド | **受け入れ条件**。数十秒以内(N1 本文) | msgpack ext(11 TU)clean ビルドが **2.46 秒**(Step 113) |
| 行/秒(代表値) | 継続計測。**ゲートではない** | 13,854(記録値。ホストの状態で 1 割以上振れる) |
| gcc -O0 比 | 継続計測。**同一 run で測るのでホストのドリフトが相殺される** | **0.397 倍** |

### なぜ絶対値をゲートから外したか

1. **20,000 行/秒には外部基準が無かった。** DESIGN 自身が「目安」と書き、その根拠を
   「典型的な gem を数十秒以内」としている。**根拠の側は満たしている**(上表)。
2. **残る構造的レバーでは届かない。** プロセス横断のヘッダトークンキャッシュは実測で
   全体の約 3%(下の選択肢 1)。目標到達に必要な +44% に対して桁が違う。
   **達成不能な目標を掲げ続けると、それに合わせて設計が歪む。**
3. **絶対値はホストを測ってしまう。** 同じ最適化前ツリーが 13,854 の日と 12,229〜12,647 の日が
   あり、master は 10,667〜10,708 だった。だから本書は繰り返し「ペアで測れ」と書いている。
   **ペアでしか意味を持たない数字は、単独のゲートに向かない。**

相対指標(「gcc -O0 の 0.5 倍」等)を条件に据える案も検討したが採らなかった。
値打ちは**達成しやすさではなく機械に依らないこと**にあるので、**ゲートではなく
見張りとして使う**方が筋が通る。

### 行/秒が明確に下がったときにすること

**「明確に下がった」の定義**: ペア計測(同一セッションで交互に 3 ラウンド、`BENCH_RUNS` は 5 以上)で
**代表値の低下が 5% 以上**、かつ **3 ラウンドとも同方向**。単発の before/after では判定しない。

そのときは、下げたまま進めてよいかを**必ず判断して記録する**。

1. **原因を帰属させる。** どの変更・どのパスかを、同一ツリーで段階的に無効化して切り分ける
   (前例: `IR::Simplify` / `IR::Promotion` を順に無効化して IR パス 6.4〜12.2%、
   バックエンド 4.4〜7% と分けた)。
2. **引き換えに何を得たかを書く。** 生成コードの速度か、正しさか、保守性か。
   **「速くなった」だけでは足りない** — 何がどれだけ良くなったかを測った値で書く。
3. **見合うかを判断する。** 見合うなら理由を `STEPS.md` に残して進む。見合わないなら
   回収する。回収しきれないなら**残りを issue に落とす**。
4. **要件に触れる判断は人間に上げる**(受け入れ条件そのものを動かす場合)。

**この手順は実際に働いた実績がある。** 最適化 2 段が 12.4% 持ち去ったとき、
「生成コードの速度をコンパイルの速度で買っていた」と帰属させ、約 71% を回収した
(本書「最適化 2 段が持ち去った分と、その回収」)。**この節はその運用を規定に昇格させたもの**である。

## 計測の定義

- **代表値** = 実 gem(json 2.21.1 / msgpack 1.8.3 / bigdecimal 4.1.2、計 16 ファイル)
  の **ファイル別「行/秒」の中央値**。
- **行** = 前処理後行数 = phase-4 出力にトークンを 1 つ以上産んだ一意な
  (ファイル, 物理行) 対の数(≒ `rubycc -E` が出す行)。
- **秒** = ソース → ELF オブジェクトのフルコンパイルを、**インプロセス・ウォーム**で
  ウォームアップ 1 回 + `BENCH_RUNS` 回計測した中央値。Ruby 起動時間を含めないのは、
  N1 が問うのがコンパイラ自身の速度だから。
- ステージングは **mkmf shim 経由の extconf**(`RUBYCC=1 gem install` と同一の
  conftest 判定)で行う。gcc で extconf すると、rubycc の conftest では無効になる
  機能マクロが有効化され、実インストールではコンパイルしないソースを測ってしまう。

計測環境: AMD Ryzen 5 4500U(6 コア)/ Linux 6.6(WSL2)/ Ruby 4.0.6 +YJIT
(および比較用に Ruby 3.4.5、YJIT 非対応ビルド)。

| Step | 施策 | 代表値(行/秒) | 備考 |
|---|---|---:|---|
| 105 | 計測基盤の整備(ベースライン) | 847 | Ruby 3.4.5(YJIT 不可) |
| 106 | Scanner の StringScanner 化 | 2,601 | 3.4.5、3.07 倍 |
| 108 | ヘッダ scan 結果のキャッシュ | 5,865 | 3.4.5、累計 6.9 倍 |
| 109 | multiple-include optimization | 6,416 | 3.4.5 |
| — | **Ruby 4.0.6 + YJIT への移行** | 11,984 | 同一コードで 2.04 倍 |
| 110 | include 解決メモ化 + membership O(1) | 12,855 | ペア計測 +6.9% |
| 111 | x86_64 emit 経路の割り当て排除 | **13,854** | ペア計測 +4.7% |
| spill-traffic-cleanup / register-allocation | (生成コードの最適化 2 段) | **↓ 12.4%** | **速度を買って速度を払った**。下記「最適化 2 段が持ち去った分」 |
| optimization-pass-throughput-1 | 関数ごとの数え上げを 1 回に | **+11.1%** | ペア計測 3 ラウンド。回帰の約 71% を回収 |

- **セッション通算 16.4 倍**(847 → 13,854)。すべて**計測駆動**で、プロファイルが

- Ruby 4.0.6 + YJIT の寄与が最大単独要因(+2.04 倍)。N1 が「YJIT 有効時」を

- **単発の before/after 比較は使えない**: 本機は ±10% ドリフトするため、

  連続実行する**ペア計測**(`BENCH_RUNS=7`)で初めて有意差が取れる。
  以後の性能ステップの採否はペア計測で判定する運用にした。

## 外部基準(gcc -O0 比、Step 112)

同一ハーネス・同一の include パス / `-D` セット / `-fPIC`・**同一の分母**で
`gcc -O0` を計測した参考値:

| | 代表値(行/秒) |
|---|---:|
| gcc -O0 | 34,874 |
| rubycc | 13,730 |
| **比** | **0.39 倍** |

gcc 側はプロセス起動込みの wall time、rubycc はインプロセス(ウォーム)なので
**絶対値は同じものを測っていない**。gcc の実速度はこれより上であり、この 0.39 倍は
rubycc に不利側の保守的な値。N1 の目標 20,000 行/秒は、この測り方での
gcc -O0 の約 0.57 倍に相当する。

## 巨大単一 TU(sqlite3 amalgamation)

N1 が「動くが遅いを許容」とした 25 万行級の実測(Step 114〜116 で 3 件のギャップを
解消して到達):

| 項目 | rubycc | gcc -O0 |
|---|---:|---:|
| 物理行数 | 261,463 | 同 |
| 前処理後行数 | 88,261 | — |
| CLI wall(起動込み) | 8.12 秒 | 4.21 秒 |
| ウォーム中央値 | 5.516 秒 | — |
| **行/秒(ベンチ指標)** | **16,001**(目標の 80.0%) | — |
| 最大 RSS | 467 MB | 277 MB |

- gcc -O0 の **1.93 倍の時間**で完走。**N6(1 TU あたり 1GB 以内)も充足**。
- 代表 gem(13,854)より速いのは、amalgamation がほぼ平坦な C でヘッダ展開の
  比率が低いため。裏を返すと gem 側の数字は ruby.h の巨大なインクルードグラフを
  毎 TU 処理する重さを反映している。
- **到達に要した修正は 3 件のみ**(Step 114 メンバ sizeof = 言語機能、
  Step 115 `pread`/`pwrite`、Step 116 `_SC_*` = ヘッダ不足)。25 万行の実コードでも
  未対応の C 構文にはほぼ当たらず、残る障壁は主にヘッダの網羅性だと実証された。

|---|---:|---:|
| msgpack ext(11 TU)の clean ビルド | 9.23 秒 | **2.46 秒**(3.76 倍) |

## ボトルネック分析(Step 111 後、stackprof / objspace)

Ruby 4.0.6 + YJIT、ウォーム状態の json parser.c フルコンパイルの自己時間:

| フレーム | 自己時間 |
|---|---:|
| `StringScanner#scan` / `#skip` / `#match?` | 合計 **24.4%** |
| GC(marking + sweeping) | **13.1%** |
| `Data#initialize`(PPToken / Front::Token 生成) | 2.7% |
| その他(個別) | いずれも ≤ 2.3% |

割り当ては 1 コンパイルあたり約 115 万オブジェクト(PPToken 144,899 /
Front::Token 51,736 を含む)。

**残っているのは「本質的な初回コスト」である**。Step 108 が再スキャン
(1,075 回中 873 回 = 81%)を、Step 109 がガード付きヘッダの再走査
(directive 処理 -79%)を消した結果、残るのは **1 TU につき約 200 個の
ユニークヘッダを 1 回ずつ字句解析する分**そのものになった。個々の残レバーは
2〜5% 級で、20,000 行/秒に必要な **+44%** には届かない。

### 残る構造的な選択肢(v1.0 では採らない)

1. ~~**プロセス横断のヘッダトークンキャッシュ**(PCH 相当)~~ — **2026-08-19 に実測で
   否定した**。`#include <ruby.h>` の 184 ヘッダで `Scanner#scan` 256.4ms に対し
   `Marshal.load` は **223.9ms(0.87 倍)**にしかならない。読み戻しても字句解析の 13%、
   全体の約 3% しか浮かず、目標に必要な +44% には遠い。**時間を食っているのは走査では
   なく約 9.4 万個のトークンオブジェクトの生成**で、読み戻しも同じ数を作るためである
   (下の GC 13.1%・115 万オブジェクトと整合する)。**選択肢 3 を先にやらない限り
   成立しない。** 詳細は `issues/cross-process-header-cache.md` の作業ログ。
2. **rmake の TU 内製化**(1 プロセスで複数 TU をコンパイルし scan キャッシュを共有):
   現行の「コンパイラのクラッシュが rmake を巻き込まない」フォーク分離設計
   (B3)と `-j` 並列の両方と衝突する。
3. **トークン表現の軽量化**(PPToken → Front::Token の変換をなくす等):
   1 コンパイルあたり約 20 万個の Data 生成を削れるが、層の分離という設計上の
   利点を失う。

## v1.0 の判断: **未達を許容する**(当時の条件に照らした記録)

代表 gem の中央値 **13,854 行/秒 = 目標 20,000 の 69.3%** で、H5 の受け入れ条件は
**未達**。それでも v1.0 で許容すると判断した。根拠:

1. **N1 の本来の要件(ユーザ体験)は満たしている**。20,000 行/秒は DESIGN 自身が
   「目安」と書いており、その根拠は「典型的な gem を数十秒以内でビルドできること」。
   実測では msgpack(11 TU)のフルビルドが 2.46 秒、コーパス 6 gem すべてが
   `RUBYCC=1 gem install` で実用的な時間内に完了している。
2. **外部基準に照らして妥当な位置にある**。Almost Pure Ruby の実装が、C で書かれた
   gcc -O0 の 0.39 倍(保守側の見積り)で動いている。
3. **N1 が明示的に許容した最悪ケースも通る**。sqlite3 amalgamation 25 万行が
   16,001 行/秒・467MB で完走(N6 も充足)。
4. **改善は出し切っており、残りは構造的変更を要する**。上記のとおり残ボトルネックは
   ユニークヘッダの初回字句解析に収斂しており、v1.0 の日程で安全に入れられる
   施策は残っていない。
5. **回帰は検出できる**。`rake bench:throughput` が数値を継続記録し、ペア計測の
   運用も定めたので、v1.0 以降に性能が落ちればすぐ分かる。

**M6 への申し送り**: 上記「構造的な選択肢」1(プロセス横断キャッシュ)を、
N4 の決定性検証とセットで評価する。目標値そのものも、gcc -O0 比という外部基準が
得られた今、「gcc -O0 の 0.5 倍」のような相対指標に置き換えるかを再検討する。

## 最適化 2 段が持ち去った分と、その回収(2026-08-15〜19)

**上の「回帰は検出できる」が実際に働いた記録である。** ヘッダキャッシュ
([`issues/cross-process-header-cache.md`](../../issues/cross-process-header-cache.md))の
着手前に現状値を測ったところ、記録の 13,854 に対し **11,063 行/秒**しか出なかった。

ペア計測(同一セッションで 3 ラウンド交互、`BENCH_RUNS=5`、`BENCH_GCC=0`):

| ラウンド | 最適化 2 段の後 | 最適化前(`94890f2`) | 比 |
|---|---:|---:|---:|
| 1 | 11,632 | 13,354 | 0.871 |
| 2 | 11,831 | 13,502 | 0.876 |
| 3 | 11,820 | 13,486 | 0.876 |

**12.4% の低下**。旧ツリーが記録値をほぼ再現したので、ホストのドリフトではない。
原因は `spill-traffic-cleanup` と `register-allocation` — **生成コードの速度を、
コンパイルの速度で買っていた**。

内訳は、同一ツリーで `IR::Simplify` / `IR::Promotion` を段階的に無効化して測った
(ツリーを差し替えないので、差はパスそのものに帰属する):

| 条件 | R1 | R2 |
|---|---:|---:|
| 現状(両パス有効) | 11,760 | 11,472 |
| `Promotion` 無効 | 12,131 | 12,162 |
| 両パス無効 | 12,517 | 12,871 |

**IR パスが 6.4〜12.2%、バックエンドが 4.4〜7%** でほぼ半々。

### 回収(`optimization-pass-throughput-1`)

1 関数あたり同じ命令列を 12〜15 回走査していた(必要なのは 3〜4 回)ので、
数え上げを 1 回にして配り回す形に変えた。**生成物は 532 ファイル(x86-64 /
AArch64 × benchmark・examples・c-testsuite)すべて sha256 一致**、つまり
生成コードは 1 バイトも変えていない。

| ラウンド | 変更後 | 変更前(master) | 最適化前 |
|---|---:|---:|---:|
| 1 | 11,762 | 10,667 | 12,229 |
| 2 | 11,982 | 10,696 | 12,245 |
| 3 | 11,895 | 10,708 | 12,647 |

**master 比 +11.1%**、最適化前比 0.864 → **0.960**(回帰の約 71% を回収)。
絶対値がこの日の前半より低いのは 3 ツリーが揃って下がっているためで、
**だからペアで見る**(上の「単発の before/after は使えない」の実例がもう 1 つ増えた)。

**残る約 4% は消せない。** stackprof で見ると、後半処理 41.7ms のうち
**バックエンドの emit が 59%**(最適化前ツリーは同じ部分が 16ms で、しかも
より長い命令列を吐いていた)。差は命令ごとに実際に増えた仕事 — 残余表の更新、
昇格 / transient の参照、オペランド形の 3 分岐であり、**それが最適化の本体**である。

## 再現方法

```sh
rake bench:throughput                                   # 既定(3 回計測)
RBENV_VERSION=4.0.6 BENCH_RUNS=7 ruby benchmark/throughput.rb   # 記録値の条件
BENCH_GCC=0 ruby benchmark/throughput.rb                # gcc 参照を切る
BENCH_WORK=/path ruby benchmark/throughput.rb           # gem ステージング先
```

性能変更の採否を判定するときは、**同一セッションで HEAD → 変更後を連続実行する
ペア計測**(`BENCH_RUNS=7`)を使うこと。単発の before/after は本機のドリフト
(±10%)に埋もれる。
